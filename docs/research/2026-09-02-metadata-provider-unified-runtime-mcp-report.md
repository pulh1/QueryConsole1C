# Runtime MCP при разработке единого metadata provider

Дата проверки: 2026-09-02.

## Итог

Runtime MCP дал ограниченный диагностический профит, но не был доказательством
работоспособности текущей ветки. Он подтвердил, что постоянный service,
`runtime.ensure` и обычный `MAIN` работают на выделенной базе. Проверить через
него новые объекты расширения нельзя: runtime был подключён к другой ИБ, в
которой нет актуального состояния ветки `feature/metadata-provider`.

Для реализации и acceptance использовались EDT-MCP, YAxUnit и Vanessa MCP.
Symbolic `CAPTURE` не использовался. Репозиторий
`C:\repo\onec-interactive-runtime` не изменялся.

## Где использован

1. Запущен постоянный service в режиме `experiment` на выделенной базе.
2. Через stdio frontend с профилем `agent` выполнен `workspace.open`.
3. `runtime.ensure(mode="experiment")` создал runtime; завершение операции
   ожидалось через `operation.wait` интервалами не более 30 секунд.
4. Повторный `runtime.ensure` переиспользовал существующий runtime.
5. Выполнен контрольный `MAIN`, присвоивший число и выведший сообщение. Он
   завершился успешно.
6. Выполнена проба обращения к новому реестру поставщиков. Она завершилась
   ошибкой исполнения, потому что runtime-база не содержит актуальное
   расширение из EDT-базы.

Runtime MCP не применялся для записи BSL, изменения ИБ, UI-тестов и замеров
производительности. Его runtime запускается с RDBG-подключением, поэтому такой
процесс нельзя оставлять живым во время финального benchmark без отладчика.

## Ошибки и ограничения

- Инструмент `workspace.capabilities` отсутствовал в фактическом наборе
  профиля `agent`, хотя `workspace.open` уже вернул capabilities.
- `code.run_inline` с параметром `outputs` был отклонён как `invalid_request`.
  Без `outputs` обычный `MAIN` работал.
- Первая реализация ожидания ошибочно пыталась вызывать отсутствующий в
  профиле `operation.status`. После перехода на один `operation.wait` цикл
  завершения работал. Это ошибка клиента проверки, не runtime service.
- После неудачной feature-пробы следующий `runtime.ensure` ещё показывал
  состояние `failed`, хотя новый простой `MAIN` уже выполнился успешно.
  Поэтому состояние ensure после ошибки нельзя считать единственным
  источником результата конкретной операции.
- Feature-проба в чужой ИБ даёт ложный отрицательный сигнал: она проверяет
  наличие развернутого расширения, а не корректность исходников текущей ветки.
- Публичного per-module hot reload в использованном контракте нет.

## Польза

- Быстро отделил работоспособность инфраструктуры runtime от готовности
  конкретной тестовой ИБ.
- Подтвердил правильный жизненный цикл: persistent service, `runtime.ensure`,
  ограниченное ожидание операции, повторное использование runtime.
- Показал расхождение фактического профиля `agent` и ожидаемого набора tools,
  которое важно учитывать в переносимых инструкциях.

## Издержки

- Без синхронизации runtime-базы с веткой проба прикладного API не является
  acceptance и может отвлекать ложной ошибкой.
- Скрытое состояние service/runtime и неполный tool profile усложняют
  диагностику по сравнению с целевым YAxUnit-тестом.
- RDBG-процесс конфликтует с требованием измерять производительность без
  отладчика и должен быть остановлен перед timed benchmark.

## Рекомендация

Использовать Runtime MCP для короткого прототипирования `MAIN` и локализации
ошибок только тогда, когда выделенная ИБ заведомо содержит проверяемую версию
расширения. Контракты семантики проверять YAxUnit, UI — Vanessa MCP, метаданные
и диагностики — EDT-MCP. Для каждого отчёта явно фиксировать, к какой ИБ был
подключён runtime, и не переносить его результат на другую базу.
