# Интеграция движка YAxUnit в QueryConsoleZUP

Дата: 2026-07-31

Статус: согласовано

## Контекст

Для перехода к модульным тестам в репозиторий QueryConsoleZUP нужно добавить
движок YAxUnit. Источником служит локальный checkout официального репозитория
`C:\dev\Slills\repositories\yaxunit` (`bia-technologies/yaxunit`). Переносится
стабильный тег `25.12`, коммит
`15f7ae557d17b59bd80daad503efd8a3114690e5`, а не текущая ветка `develop`.

Основное расширение QueryConsoleZUP и движок должны храниться в одном Git-
репозитории, но оставаться разными EDT-проектами. Будущее расширение с тестами
и адаптация skills не входят в эту итерацию.

## Цели

1. Добавить воспроизводимую копию стабильного EDT-проекта YAxUnit 25.12.
2. Подготовить проект движка к привязке к той же базовой конфигурации, что и
   `QueryConsoleZUP`.
3. Сохранить возможность запуска и отладки тестов через установленный EDT-MCP.
4. Зафиксировать версию, происхождение, лицензию и локальные адаптации движка.
5. Оставить обновление YAxUnit изолированным от будущего тестового кода.

## Не входит в работу

- создание расширения `QueryConsoleZUPTests`;
- написание или запуск первых тестов;
- перенос или адаптация `yaxunit-test-writer` и других skills;
- установка отдельного YAxUnit-плагина для EDT;
- перенос документации, CI, fixtures, собственных тестов и инструментов сборки
  из полного upstream-репозитория;
- изменение BSL, метаданных и форм основного расширения `QueryConsoleZUP`;
- изменение исходного репозитория `C:\dev\Slills\repositories\yaxunit`.

## Рассмотренные варианты

### 1. Копия EDT-проекта движка в текущем репозитории — выбран

Из тега `25.12` переносится только `exts/yaxunit/` в корневой каталог
`yaxunit/`. Вложенный Git-репозиторий и submodule не создаются.

Преимущества: один checkout проекта, простая работа EDT, зафиксированное
содержимое версии, отсутствие зависимости от доступности внешнего репозитория
при сборке и запуске. Обновление выполняется отдельным контролируемым сравнением
с новой стабильной версией.

### 2. Git submodule полного upstream-репозитория — отклонён

Этот вариант сохраняет upstream-историю, но добавляет обязательную работу с
submodule и размещает нужный EDT-проект внутри лишней структуры
`exts/yaxunit/`. Ошибки инициализации submodule сделали бы тестовое окружение
невоспроизводимым для обычного checkout.

### 3. Объединение движка с тестовым расширением — отклонено

Такой вариант даёт подсказки YAxUnit внутри тестового проекта, но смешивает
сторонний движок и проектные тесты. Обновления движка потребовали бы постоянного
трёхстороннего слияния. На первом этапе важнее независимые границы.

## Структура репозитория

После переноса верхний уровень выглядит так:

```text
QueryConsoleZUP/
├── QueryConsoleZUP/       # существующее основное расширение
├── yaxunit/               # EDT-проект движка YAxUnit 25.12
├── features/              # существующие сценарии Vanessa Automation
├── THIRD_PARTY_NOTICES.md
└── ...
```

Будущий `QueryConsoleZUPTests/` будет проектироваться отдельно и не создаётся
этой работой.

## Состав переноса

В `yaxunit/` копируются из дерева тега `25.12`:

- `.project`;
- `.settings/`;
- `DT-INF/`;
- `src/`.

Для соблюдения Apache License 2.0 рядом с движком сохраняются upstream-файлы
`LICENSE` и `COPYRIGHT`. В `yaxunit/UPSTREAM.md` фиксируются URL, тег, полный
commit SHA, исходный путь `exts/yaxunit/`, дата интеграции и перечень локальных
адаптаций. Корневой `THIRD_PARTY_NOTICES.md` дополняется сведениями о YAxUnit.

Из upstream не копируются `.git`, `.github`, `.cursor`, `.vscode`,
`custom_modes`, `documentation`, `fixtures`, `memory-bank`, `tests`, `tools`,
корневые настройки анализаторов и другие файлы, не требуемые EDT-проекту
движка.

## EDT-интеграция

Проект сохраняет имя `yaxunit` из upstream `.project` и остаётся расширением с
назначением `AddOn`, префиксом `ЮТ` и режимом совместимости расширения `8.3.10`.
Режим совместимости не повышается: YAxUnit официально поддерживает платформу
начиная с 8.3.10.

Локально адаптируется `yaxunit/DT-INF/PROJECT.PMF`:

- `Runtime-Version` устанавливается в `8.3.24`, как у QueryConsoleZUP;
- `Base-Project` устанавливается в
  `База_разработки_исполняемых_представлений_демо_ЗУП`.

После появления файлов проект нужно один раз импортировать в текущий workspace
EDT как существующий проект. У доступного EDT-MCP нет операции импорта готового
EDT-проекта из `.project`; `import_configuration_from_xml` для этого не подходит,
поскольку принимает выгрузку XML Конфигуратора, а YAxUnit уже находится в
формате EDT. Поэтому импорт остаётся явной ручной проверкой после переноса.

YAxUnit и `QueryConsoleZUP` привязываются к одной базовой конфигурации и одной
информационной базе. После установки расширения YAxUnit в информационную базу
пользователь вручную снимает безопасный режим и защиту от опасных действий, как
требует официальная инструкция YAxUnit.

## Запуск через EDT-MCP

В текущем EDT-MCP фактически доступен `run_yaxunit_tests`. Для запуска можно
использовать существующую runtime-client конфигурацию
`QueryConsoleZUP Тонкий клиент` базового проекта.

Обычный запуск выполняется с `updateBeforeLaunch=true` и `updateScope=all`.
EDT-MCP пересчитывает базовую конфигурацию и зависимые расширения, обновляет
информационную базу, запускает 1С с параметром `RunUnitTests`, ожидает JUnit XML
и возвращает Markdown-отчёт. Для отладки используется тот же вызов с
`debug=true`, после установки breakpoint.

Сам перенос движка не запускает тесты: до создания тестового расширения нет
проектных тестовых модулей, а до ручного импорта проекта и настройки безопасного
режима запуск не является воспроизводимой автоматической проверкой.

## Обновление движка

Обновление выполняется только на другой явно выбранный стабильный тег:

1. извлечь `exts/yaxunit/` из нового тега во временный каталог;
2. сравнить его с зафиксированным upstream-тегом `25.12`;
3. перенести upstream-изменения без потери локальной адаптации `PROJECT.PMF`;
4. обновить `UPSTREAM.md` и `THIRD_PARTY_NOTICES.md`;
5. выполнить проверки EDT и пробный запуск существующих тестов.

Локальные изменения BSL или метаданных внутри `yaxunit/src/` без отдельного
обоснования не допускаются.

## Проверка реализации

1. Сверить SHA тега `25.12` с
   `15f7ae557d17b59bd80daad503efd8a3114690e5`.
2. Сравнить каждое перенесённое содержимое `.project`, `.settings/`, `DT-INF/`
   и `src/` с `git archive 25.12`, кроме двух документированных строк
   `PROJECT.PMF`.
3. Проверить отсутствие вложенного `.git` и файлов полного upstream-
   репозитория вне согласованного состава.
4. Проверить наличие `LICENSE`, `COPYRIGHT`, `UPSTREAM.md` и уведомления в
   `THIRD_PARTY_NOTICES.md`.
5. Проверить `.project`, `PROJECT.PMF` и ключевые свойства
   `Configuration.mdo` точечным чтением.
6. Выполнить `git diff --check` и проверить фактический список добавленных
   файлов.
7. Подтвердить, что существующие BSL, метаданные, формы, features и skills не
   изменились.
8. После ручного импорта убедиться через EDT-MCP, что проект `yaxunit` открыт,
   имеет природу `V8ExtensionNature` и связан с правильной базой.
9. После установки расширения в информационную базу проверить пробный вызов
   `run_yaxunit_tests`; отсутствие проектных тестов не должно интерпретироваться
   как успешное покрытие QueryConsoleZUP.

## Критерии готовности

- в корне репозитория находится отдельный EDT-проект `yaxunit/` из стабильного
  YAxUnit 25.12;
- полный upstream SHA, лицензия, copyright и локальные адаптации зафиксированы;
- движок подготовлен к работе с базовым проектом и платформой QueryConsoleZUP;
- основной проект и существующие сценарии не изменены;
- репозиторий не содержит вложенного Git-репозитория и нерелевантных частей
  upstream;
- ручные шаги импорта в EDT, установки в информационную базу и снятия защит
  перечислены явно;
- после ручной настройки движок можно запускать и отлаживать через существующий
  EDT-MCP и runtime-client launch-конфигурацию.
