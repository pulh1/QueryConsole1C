# Единая граница поставщиков метаданных

Дата: 2026-09-02

Статус: утверждённый дизайн, ожидает просмотра письменной спецификации

## Место в архитектуре

Эта спецификация уточняет
`2026-08-30-metadata-provider-semantics-ui-design.md` и
`2026-08-31-lazy-metadata-provider-semantics-design.md`. Она заменяет
разделение доставки на два PR и закрывает обнаруженные
после реализации утечки абстракции. Контракт ленивой
семантики, границы временных таблиц и вложенных запросов,
а также текущая визуальная иерархия конструктора сохраняются.

## Проблема

Зафиксированная семантика уже маршрутизирует именованные
таблицы и поля через реестр. Однако UI-часть осталась
привязана к двум штатным поставщикам:

- UI-контекст возвращает реестр и оба конкретных provider object;
- корень `Представления` создаётся фасадом вручную;
- выбор `ДочерниеЭлементы()` выполняется по конкретному
  `ВидИсточника`;
- форма параметров напрямую вызывает legacy-модуль
  `ПоставщикИсполняемыхПредставлений`;
- тесты UI проверяют два конкретных provider object, а не
  подстановку произвольного поставщика.

Из-за этого новый поставщик нельзя показать в UI только регистрацией
в реестре, а нейтральный контракт параметров не используется
конечным consumer-ом.

## Цели

1. Оставить в UI-контексте только реестр.
2. Перенести агрегацию каталога и маршрутизацию его дочерних узлов
   в реестр.
3. Перевести форму параметров на нейтральное описание таблицы.
4. Доказать границу через мок-поставщик в семантике и UI.
5. Доставить семантику и UI одной веткой и одним PR в `master`.

## Не входит в работу

- отдельный поставщик временных таблиц или вложенных запросов;
- новый корневой узел по имени поставщика;
- изменение lexer, parser, AST или модели источников;
- новый редактор параметров стандартных виртуальных таблиц;
- глобальный, session-level или межоперационный кэш provider object;
- изменение публичного API legacy-модуля
  `ПоставщикИсполняемыхПредставлений`;
- закрытие старых PR до публикации и проверки заменяющего PR.

## Архитектура

### Composition root

Штатный состав поставщиков по-прежнему создаёт manager module
`РеестрПоставщиковМетаданныхТаблиц`. Для production UI
`НовыйКонтекстМетаданныхUI()` создаёт штатный реестр через
эту фабрику и возвращает структуру только со свойством `Реестр`.

Для тесов фасад не создаёт моки сам. Он принимает контекст с любым
уже созданным реестром. Этого достаточно для проверки независимого
поставщика без тестовых ветвлений в production-коде.

### Каталог реестра

Реестр хранит не только индекс сегментов, но и неизменяемый массив
инициализированных поставщиков в порядке композиции. Этот порядок
определяет порядок корней в UI.

Публичные операции реестра:

```text
КорневыеЭлементыКаталога()
ДочерниеЭлементыКаталога(МаршрутКаталога)
```

`КорневыеЭлементыКаталога()` обходит поставщиков в порядке композиции и
объединяет их корневые элементы. Штатный executable-provider сам возвращает
текущий корень `Представления`; реестр и UI не знают это имя.

Каждый transport-safe элемент каталога получает нейтральное поле
`МаршрутКаталога`. Значение создаёт реестр из одного зарегистрированного
сегмента поставщика и opaque идентификатора узла. UI возвращает его без разбора в
`ДочерниеЭлементыКаталога()`. Сырой provider object, platform object и
`ДанныеПоставщика` в маршрут не входят.

Маршрут — детерминированная строка вида
`<сегмент>|<идентификатор>`. Сегменты являются идентификаторами языка
запросов и не содержат `|`; разделяется только первое вхождение, поэтому
opaque идентификатор может содержать разделитель. Формат строки закрыт внутри
реестра; UI не создаёт и не разбирает его.

Для группы UI-фасад сохраняет маршрут в существующей строковой колонке
`Имя`, которая не отображается. Колонка `Представление` остаётся видимым
заголовком. Для таблицы `Имя` по-прежнему содержит полное имя таблицы. Новая
колонка формы и изменение `Form.form` не требуются.

### Контракт поставщика каталога

Поставщик по-прежнему реализует:

```text
ДочерниеЭлементы(ИдентификаторРодителя = Неопределено)
```

Корни каталога тоже возвращаются этим методом с `Неопределено`.
Для executable-provider это означает, что он возвращает один transport-safe
корень `Представления`, а его нынешние группы возвращаются на следующем
уровне. Стандартный provider продолжает возвращать свои текущие корни.

Состав транспортного элемента каталога:

```text
Идентификатор
ИмяТаблицы
Представление
ЭтоГруппа
ЕстьДочерние
ВидИсточника
МаршрутКаталога
```

Для детей вложенного поля используется описание поля, а не элемент
каталога. `ДанныеПоставщика` остаются только в серверных описаниях
таблиц, полей и параметров.

### Параметры таблицы

Форма параметров получает полное нейтральное описание через
`Реестр.ОписаниеТаблицы(ИмяТаблицы)` и не вызывает legacy-модуль.
Она строит отображение по `ОписаниеТаблицы.Параметры`.

Для того чтобы сохранить текущее поведение фильтра и отбора, нейтральное
описание параметра должно нести все данные, нужные форме:

```text
Имя
ВидПараметра
ТипЗначения
Обязательный
Варианты
Поля
ДопустимыеТипы
ДопустимПараметрЗапроса
ЗначениеПоУмолчанию
```

`Поля` параметра содержат не описания полей таблицы, а специализированные
transport-safe структуры `Имя, Обязательный, Устарело`. Это сохраняет
текущую семантику полей ВТ-фильтра. Для отбора обязательность и устаревание
получают значения по умолчанию.

`МетаданныеТаблицЗапроса` расширяет фабрики этими transport-safe
свойствами. Оба штатных поставщика возвращают один и тот же контракт.
`ДанныеПоставщика` форма не читает.

Команда открытия параметров остаётся привязанной к доменному типу модели
`ИсполняемоеПредставление`: существующая форма сохраняет параметры именно в
эту модель. Это не идентичность metadata provider-а. Прямой вызов legacy-поставщика
из формы удаляется, но модель источника и формат сохраняемых параметров не меняются.
Редактор параметров стандартных виртуальных таблиц остаётся отдельной будущей задачей.

### Семантическая граница

При наличии реестра все именованные внешние источники разрешаются
только через `НайтиТаблицу()` и `НайтиПоле()`. Полный `ОписаниеТаблицы()`
не вызывается из semantic path.

`СемантическийАнализВыраженийУтилиты.НайтиПолеВИсточнике()` остаётся единым
диспетчером по типам источника модели. Это не является утечкой provider-а:
метод знает доменные типы модели, но не знает имена или типы конкретных
поставщиков. Его ветвления имеют следующий контракт:

- `ИсточникДанныхВложенныйЗапрос` читает колонку вложенной модели;
- `ИсточникДанныхВременнаяТаблица` читает локальное `ОписаниеВТ`;
- `ИсточникДанныхТаблицаЗначений` сохраняет локальную семантику неизвестной схемы;
- `ИсточникДанныхТаблица` и `ИсполняемоеПредставление` немедленно делегируют
  `Реестр.НайтиПоле()`.

Вызывающие места диспетчера проверяются отдельно: поиск неквалифицированного
поля по всем источникам, `ТипПоляПоИмени()` и semantic visitor при обработке
`ПолеИсточника`. Разыменование ссылочного типа через
`ТипЭлементаРазыменованияИзОписанияТипов()` также ищет поле только через реестр.

Неквалифицированное поле не может создаваться в неизвестной схеме
внешней временной таблицы или таблицы значений, если оно уже
однозначно разрешилось в другом источнике. Только квалифицированное
обращение к такому локальному источнику может добавить в него колонку
произвольного типа по текущему compatibility contract.

`ПостроительМоделиЗапроса` и `ОбработкаПредставлениеЗапросов` получают краткое
описание именованной таблицы только через `НайтиТаблицу()`. Чтение
`ДанныеПоставщика` разрешено только server-side adapter-у штатных исполняемых
представлений после проверки `ВидИсточника`. Это явное исключение для моста к
существующему runtime-контракту, а не обещание произвольному поставщику
исполнения таблицы. UI и semantic visitor это поле не читают.

### Кэши и lifecycle

Владельцем всех кэшей остаётся конкретный поставщик. Реестр хранит
только индексы маршрутизации и список поставщиков. UI создаёт один реестр
на одну серверную операцию формы. Межоперационное переносимое состояние
не вводится. Это ограничивает кэши одной операцией, но не передаёт stateful
objects в данные формы.

## Ошибки и границы

- коллизии сегментов остаются ошибками инициализации;
- неизвестный маршрут каталога возвращает пустой массив;
- неизвестная таблица возвращает `Неопределено`;
- provider не возвращает `ДанныеПоставщика` в элементе каталога;
- UI не разбирает маршрут и не полагается на его формат;
- пустое или неизвестное нейтральное описание прекращает открытие редактора с
  той же прикладной ошибкой, которую формирует текущий серверный consumer;
- старая форма параметров не получает legacy fallback при наличии реестра;
- ошибки provider-а не маскируются повторным прямым lookup.

## Проверка

### YAxUnit

1. Мок-поставщик с сегментом, отличным от штатных, доказывает полный path
   `парсер → обработка источника → semantic visitor`. Счётчики шпиона
   показывают один `НайтиТаблицу()`, один `НайтиПоле()` и ноль вызовов
   `ТаблицаСуществует()` и `ОписаниеТаблицы()`.
2. Отдельные тесты `НайтиПолеВИсточнике()` покрывают вложенный запрос,
   внутреннюю и внешнюю ВТ, таблицу значений, штатную таблицу и исполняемое
   представление. Для локальных источников счётчики provider-а остаются нулевыми.
3. Тесты derived contexts доказывают повторное использование того же реестра
   во вложенном запросе, параметрах виртуальной таблицы и выражениях дополнения
   периодами.
4. Пустой реестр доказывает отсутствие fallback к штатной схеме и
   legacy-поставщику.
5. Неквалифицированное поле не загрязняет неизвестную схему внешней ВТ или
   таблицы значений.
6. UI-фасад получает корень и дочернюю таблицу мок-поставщика только через
   реестр.
7. UI-строки и маршруты не содержат `ДанныеПоставщика` и provider object.
8. Форма параметров получает нейтральные параметры через реестр и не вызывает
   legacy-поставщик.
9. Штатные standard и executable catalog сохраняют текущий порядок, флаги и
   ленивое раскрытие.

### Приемочные проверки

- целевые YAxUnit-наборы, затем полный набор;
- EDT diagnostic delta для изменённых модулей;
- runtime smoke с фактически загруженной общей веткой;
- Vanessa UI-сценарии каталога и параметров без отладчика;
- новый полный замер parser-to-semantics нужен только если изменится semantic hot path;
- независимое code review перед публикацией PR.

## Доставка

Вся работа выполняется в `feature/metadata-provider`, которая содержит
обе прежние ветки. После полной проверки создаётся один ready PR в
`master`. PR #76 и #77 закрываются только после того, как заменяющий PR
опубликован и не теряет их историю коммитов.

## Критерии готовности

- UI-контекст не публикует конкретные provider objects;
- UI-каталог агрегируется и маршрутизируется реестром;
- новый мок-поставщик появляется в каталоге без изменения UI-фасада;
- нейтральные описания параметров достаточны для текущей формы;
- в form data не попадают provider objects, platform objects и `ДанныеПоставщика`;
- полный semantic path использует только точечные методы provider-а;
- неквалифицированные поля не загрязняют неизвестные локальные схемы;
- целевые и полные тесты зелёные;
- EDT, runtime и Vanessa gaps зафиксированы фактически;
- заменяющий PR готов к review до закрытия старых PR.
