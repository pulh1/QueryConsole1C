# Поставщики метаданных таблиц запроса: семантика и UI

Дата: 2026-08-30

Статус: утверждённый дизайн, ожидает просмотра письменной спецификации

## Контекст

Ветка `metadata-provider` содержит полезную идею реестра поставщиков, но не
может быть перенесена целиком на текущий `master`. Она отстаёт от `master`,
пересекается с изменившейся моделью источников и содержит подтверждённые
дефекты:

- нейтральное описание вложенной таблицы несовместимо с semantic visitor;
- заявленная интеграция с формами отсутствует;
- параметры стандартных виртуальных таблиц всегда возвращаются пустыми;
- отдельный поставщик временных таблиц дублирует уже существующий локальный
  контекст пакета запроса;
- lifecycle поставщиков и регистрация не образуют устойчивого публичного
  контракта.

Новая реализация строится от текущего `master` и переносит из старой ветки
только проверенные архитектурные идеи. Доставка разделяется на две
последовательные части: сначала семантика, затем UI.

## Цели

1. Ввести единый серверный контракт получения метаданных именованных таблиц
   запроса.
2. Подключить к нему стандартные таблицы платформы и исполняемые
   представления.
3. Сохранить локальную семантику временных таблиц, вложенных запросов,
   параметров-таблиц значений и источников внешнего запроса.
4. Исправить разрешение вложенных полей и параметров виртуальных таблиц без
   изменения lexer, parser и AST.
5. Во второй фазе сохранить существующую иерархию и поведение деревьев форм,
   заменив прямой доступ к разнородным источникам серверным фасадом.
6. Зафиксировать владельцев кэшей и lifecycle так, чтобы реестр оставался
   маршрутизатором, а не хранилищем описаний.
7. Проверить решение YAxUnit-тестами, runtime-прототипами на реальной базе и
   диагностическим delta EDT.

## Не входит в работу

- изменение lexer, parser, grammar или AST;
- отдельный поставщик временных таблиц;
- перенос старой ветки через merge или wholesale cherry-pick;
- новый корневой UI-узел по имени поставщика;
- изменение публичного API `ПоставщикИсполняемыхПредставлений`;
- отрицательный кэш неизвестных таблиц;
- серверный кэш дерева формы;
- per-module hot reload;
- изменение бизнес-данных целевой базы;
- обязательная зависимость production-кода от MCP runtime.

## Стратегия поставки

Работа выполняется в двух последовательных ветках:

1. `feature/metadata-provider-semantics` создаётся от текущего `master` и
   содержит объекты поставщиков, реестр, нейтральные описания, semantic
   integration и серверные YAxUnit-тесты.
2. `feature/metadata-provider-ui` создаётся от принятой ветки semantics и
   содержит каталог поставщиков для UI, адаптацию серверного фасада и формы.

UI-ветка не дублирует и не переопределяет semantic contract. Она расширяет
готовых поставщиков каталогом и переводит на него существующих form callers.

## Именование

По прямому решению владельца проекта новые объекты создаются без префикса
`КОНС_`:

- data processor `РеестрПоставщиковМетаданныхТаблиц`;
- data processor `ПоставщикМетаданныхСтандартныхТаблиц`;
- data processor `ПоставщикМетаданныхИсполняемыхПредставлений`;
- common module `МетаданныеТаблицЗапроса`.

Это сознательное исключение из общего правила `QueryConsoleZUP/AGENTS.md`.
Исключение относится только к перечисленным объектам этой задачи и не меняет
правило именования для остальных новых объектов.

## Архитектура

### Реестр

`РеестрПоставщиковМетаданныхТаблиц` является stateful data processor object.
Его manager module создаёт объект, формирует список штатных поставщиков и
однократно вызывает инициализацию.

Object module хранит private `ПоставщикиПоСегментам`. После завершения
инициализации индекс не изменяется. Публичной операции регистрации в уже
работающий реестр нет.

Для тестов и будущих composition roots manager factory допускает передать
явный список поставщиков вместо штатного списка. Это не открывает mutable
runtime-регистрацию: переданный набор целиком фиксируется во время создания
реестра.

Первый сегмент полного имени таблицы нормализуется через `ВРег`. Один сегмент
может принадлежать только одному поставщику. Коллизия обнаруживается до
публикации реестра и завершает инициализацию исключением с именем сегмента и
обоих поставщиков.

Реестр не хранит описания таблиц и не вызывает `ТаблицаСуществует()` перед
каждым `ОписаниеТаблицы()`. Он выбирает поставщика по сегменту и сразу
делегирует операцию. Это исключает двойной raw lookup при отсутствии
отрицательного кэша.

### Контракт поставщика в фазе semantics

Каждый конкретный поставщик реализует dynamic contract:

```text
Инициализировать()
ИмяПоставщика()
Сегменты()
ТаблицаСуществует(ИмяТаблицы)
ОписаниеТаблицы(ИмяТаблицы)
```

Версионирование контракта не вводится. `Инициализировать()` вызывается один
раз до регистрации сегментов. Повторный вызов на том же объекте не является
частью публичного контракта.

`ТаблицаСуществует()` — самостоятельная проверка для consumers, которым не
нужно описание. `ОписаниеТаблицы()` самостоятельно возвращает описание либо
`Неопределено`; caller не обязан предварительно вызывать
`ТаблицаСуществует()`.

### Нейтральное описание таблицы

`МетаданныеТаблицЗапроса` содержит только stateless factories, validators и
конверсионные утилиты. Он не владеет схемой, реестром или кэшами.

Описание таблицы является структурой со свойствами:

```text
ИмяТаблицы
ИмяПоставщика
ВидИсточника
Представление
Поля
Параметры
ДанныеПоставщика
```

`ДанныеПоставщика` — opaque server-only значение. Оно может использоваться
внутри конкретного поставщика или серверного adapter-а, но никогда не
передаётся в форму и не входит в transport DTO.

Описание поля содержит:

```text
Имя
Представление
ВидПоля
ТипЗначения
Роль
Поля
ДанныеПоставщика
```

`ВидПоля` принимает значения `ОбычноеПоле` и `ВложеннаяТаблица`. Для
вложенной таблицы дочерние поля находятся в `Поля`; строковый marker вместо
платформенного объекта не используется как признак вложенности. Semantic
visitor ветвится по `ВидПоля` и не вызывает `.Типы()` для вложенной таблицы.

Описание параметра виртуальной таблицы содержит:

```text
Имя
ВидПараметра
ТипЗначения
Обязательный
Варианты
Поля
ДанныеПоставщика
```

Стандартный provider конвертирует фактические свойства платформенного
параметра, включая имя, вид, тип значения, варианты и доступные поля.
Свойства, отсутствующие у конкретного платформенного параметра, получают
нейтральное пустое значение, а не приводят к удалению самого параметра.

Factories common module всегда создают новые коллекции. Описания разных
таблиц и полей не разделяют mutable arrays или structures.

### Стандартный поставщик

`ПоставщикМетаданныхСтандартныхТаблиц` является единственным владельцем
каталога `СхемаЗапроса.ДоступныеТаблицы` в пределах экземпляра реестра.
Контекст semantic analysis может хранить схему разбираемого запроса для
топологии пакета, но не создаёт и не передаёт consumers второй каталог
метаданных таблиц.

Поставщик владеет:

- экземпляром `СхемаЗапроса`;
- `ДоступныеТаблицы` этой схемы;
- positive cache `ОписанияТаблицПоИменам`.

Ключ кэша — нормализованное полное имя таблицы. Неизвестные таблицы не
кэшируются. Описание создаётся рекурсивно: обычные поля, вложенные таблицы и
параметры преобразуются в нейтральные structures.

### Поставщик исполняемых представлений

`ПоставщикМетаданныхИсполняемыхПредставлений` является adapter-ом к
существующему `ПоставщикИсполняемыхПредставлений`. Публичный API существующего
модуля не меняется.

Raw-описания продолжает кэшировать существующий
`ПоставщикИсполняемыхПредставленийПовтИсп` с reuse `DuringSession`. Новый
provider не создаёт второй raw cache. Он может хранить только positive cache
результата преобразования raw-описания в нейтральный формат внутри своего
экземпляра.

## Граница локальных источников

Реестр разрешает только именованные внешние таблицы. Следующие источники
остаются частью локального semantic context:

- временные таблицы текущего пакета;
- вложенные запросы;
- параметры с таблицами значений;
- aliases текущего оператора;
- разрешённые источники внешнего запроса.

Порядок разрешения поля или источника:

1. aliases и локальные источники текущего контекста;
2. локальные источники внешнего запроса, если они разрешены;
3. реестр именованных внешних таблиц.

Отдельного provider-а временных таблиц нет. Локальные источники не попадают в
provider caches и не могут утечь между верхнеуровневыми контекстами.

## Lifecycle

Один верхнеуровневый цикл обработки или построения запроса создаёт один
реестр. Его переиспользуют:

- контекст верхнего запроса;
- `КонтекстОбработкиВложенногоЗапроса()`;
- `КонтекстОбработкиПараметровВиртуальнойТаблицы()`;
- все derived contexts обработки выражений;
- все операции одного lifecycle `ПостроительМоделиЗапроса`.

Новый реестр не создаётся в `ДобавитьИсточник()` и не создаётся на каждое
разыменование. Новый независимый верхнеуровневый запрос получает новый
реестр и новые instance caches.

## Разрешение и ошибки

Неизвестный сегмент или неизвестная таблица возвращают `Неопределено` из
реестра. Compatibility fallback к прямому старому lookup разрешён только
тогда, когда caller получил legacy context без свойства реестра.

Если реестр присутствует и вернул `Неопределено`, прямой lookup не
повторяется. Это сохраняет наблюдаемость дефекта adapter-а и исключает двойное
разрешение.

Именованный источник проверяется во время обработки источников, даже если
запрос не обращается к его полям. Поведение entry points:

- `ПостроительМоделиЗапроса` сохраняет пользовательскую ошибку
  `Таблица ... не найдена`;
- полный semantic path завершает обработку неизвестного именованного
  источника семантической ошибкой с именем таблицы;
- низкоуровневые registry/provider methods возвращают `Неопределено` и не
  формируют UI-сообщения;
- коллизия сегментов является ошибкой инициализации, а не ошибкой отдельного
  запроса.

Регистрация всех providers завершается до первого resolve. Частично
инициализированный реестр не публикуется consumers.

## Фаза 1: semantics

### Новые объекты

Добавляются три data processors и один common module, перечисленные в разделе
«Именование». Manager modules отвечают за создание и composition root;
stateful contract и кэши находятся в object modules.

### Изменяемые consumers

`ОбработкаМоделиЗапроса`:

- создаёт реестр в верхнеуровневом context factory;
- передаёт тот же реестр во все derived contexts;
- удаляет прямое владение вторым каталогом `ДоступныеТаблицыИБ` там, где
  метаданные теперь разрешаются через provider;
- сохраняет текущую локальную обработку ВТ, вложенных запросов и aliases.

`СемантическийАнализВыраженийУтилиты`:

- разрешает именованные таблицы через реестр;
- возвращает нейтральное описание поля;
- не смешивает raw platform objects и neutral descriptors.

`СемантическийАнализВыраженийПосетитель`:

- различает обычное поле и вложенную таблицу по `ВидПоля`;
- рекурсивно разрешает дочернее поле neutral descriptor-а;
- сохраняет текущий output contract semantic analysis.

`ОбработкаПредставлениеЗапросов`:

- использует реестр для нового context;
- применяет прямой старый lookup только при полном отсутствии реестра.

`ПостроительМоделиЗапроса`:

- создаёт один реестр на lifecycle builder-а;
- использует его для всех операций добавления и раскрытия источников;
- сохраняет обход `МодельЗапросаУтилиты.ВсеИсточникиОператора()` и актуальную
  join topology.

## Фаза 2: UI

### Каталог поставщика

Во второй фазе dynamic contract поставщика расширяется методом:

```text
ДочерниеЭлементы(ИдентификаторРодителя = Неопределено)
```

Метод возвращает массив transport-safe structures:

```text
Идентификатор
ИдентификаторРодителя
ИмяТаблицы
Представление
ЭтоГруппа
ЕстьДочерние
ВидИсточника
```

Идентификатор стабилен в пределах каталога поставщика. Для группы
`ИмяТаблицы = Неопределено`. Для leaf полное имя находится в `ИмяТаблицы`.
Поля таблицы не копируются в catalog node: при раскрытии leaf вызывается
`ОписаниеТаблицы()`, что сохраняет lazy loading.

В catalog nodes нет `ДанныеПоставщика`, raw platform objects и ссылок на
stateful provider. Это позволяет передавать их между сервером и формой без
неявной сериализации внутреннего состояния.

### Серверный фасад формы

`КонструкторЗапросовФормы` остаётся единственным adapter-ом между providers и
формами. Он:

- получает provider catalog nodes и neutral table descriptions на сервере;
- записывает результат непосредственно в существующие строки
  `ДанныеФормыДерево`;
- сохраняет существующие колонки, flags и изображения форм;
- не помещает `ДанныеПоставщика` или raw platform objects в данные формы;
- продолжает отдельно добавлять model-local источники.

Новый универсальный клиентский DTO и новая корневая группа поставщика не
вводятся. Текущая форма дерева является transport contract UI.

### Иерархия

Корневой порядок сохраняется:

1. существующие platform groups стандартных таблиц;
2. группа `Представления` с текущими подгруппами;
3. группа `Временные таблицы` последней и только при наличии ВТ.

Вложенные запросы и таблицы значений остаются узлами model-local sources, а
не дочерними элементами provider root. Поставщики не получают собственные
видимые корневые узлы.

Lazy loading сохраняется для platform groups, представлений, таблиц и
вложенных полей. Узел-заглушка удаляется только при первом фактическом
раскрытии.

### Формы и callers

Изменяются server calls в формах `КонструкторЗапросов` и
`РедакторВыражений`. Обязательному regression coverage подлежат все шесть
текущих вызовов
`КонструкторЗапросовФормы.ЗаполнитьДочерниеЭлементыДереваДоступныхТаблиц`:

- дерево доступных таблиц;
- дерево источников;
- редактор выражений;
- деревья группировки;
- условия и итоги;
- порядок и связанные secondary trees.

Структурные изменения `Form.form` не выполняются, если существующих columns и
flags достаточно. Необходимость любого изменения формы подтверждается
отдельной EDT form inspection до правки.

## Client/server и безопасность

Все providers, registry, raw metadata и caches работают на сервере. Клиент
получает только существующее дерево формы и простые значения catalog nodes.

`ДанныеПоставщика` запрещено:

- помещать во временное хранилище для формы;
- включать в возвращаемую server function structure;
- сериализовать в form attributes;
- использовать как client-side identity.

Runtime-прототипы выполняются только в `experiment` mode и не изменяют
бизнес-данные. Любая проверка, способная записать данные, требует отдельного
доказанного isolation boundary и не входит в эту задачу.

## Тестирование

### YAxUnit: semantics

Новые и расширенные server tests проверяют:

- стандартную таблицу и обычное поле;
- вложенную таблицу и рекурсивное поле;
- параметры виртуальной таблицы, включая варианты и доступные поля;
- исполняемое представление, его поля и параметры;
- неизвестный сегмент и неизвестную таблицу;
- коллизию сегментов при инициализации;
- отсутствие двойного lookup `ТаблицаСуществует()` + `ОписаниеТаблицы()`;
- positive cache и отсутствие negative cache;
- один registry во вложенном запросе и параметрах виртуальной таблицы;
- независимые caches двух верхнеуровневых contexts;
- регрессии временных таблиц, вложенных запросов и таблиц значений;
- присоединённый источник через `ВсеИсточникиОператора()`;
- semantic error для неизвестной таблицы без обращения к её полям.

Основной test runner — `EDT-MCP run_yaxunit_tests`. Runtime inline probes не
заменяют YAxUnit и не считаются доказательством regression gate.

### YAxUnit и ручные проверки: UI

Проверяются:

- точный порядок и имена корневых групп;
- lazy раскрытие стандартных platform groups;
- `Представления` и существующие подгруппы;
- условное появление последней группы `Временные таблицы`;
- добавление стандартного и provider-backed источника;
- раскрытие обычных и вложенных полей;
- все шесть form callers;
- запрос с присоединённым источником;
- отсутствие raw provider data в form attributes.

Два существующих server tests деревьев, пропущенные из-за различия
`ДеревоЗначений` и `ДанныеФормыДерево`, не считаются достаточной UI-проверкой.
Финальный gate включает ручной сценарий управляемой формы в клиенте 1С.

### EDT diagnostics

До первой metadata-правки фиксируется baseline diagnostics открытого проекта
расширения. После каждой фазы сравнивается relevant delta, а не требование
нулевых ошибок всего workspace.

Если проект `QueryConsoleZUP` не открыт в EDT, metadata implementation и
diagnostic gate не начинаются. Сначала создаётся или подключается корректный
EDT workspace с базовой конфигурацией, расширением, `yaxunit`, приложением и
launch configuration.

## Использование onec-runtime MCP

MCP является вспомогательным runtime-контуром, а не production dependency и
не основным test runner.

До реализации через `MAIN` фиксируются только факты платформы:

- структура `СхемаЗапроса` и доступных таблиц;
- свойства обычных и вложенных полей;
- свойства параметров виртуальных таблиц;
- transportability значений, которые планируется оставить server-only.

После загрузки каждой semantic slice выполняются ограниченные smoke-probes:

- создание registry и разрешение одной стандартной таблицы;
- разрешение одного исполняемого представления;
- повторный lookup для наблюдения warm cache;
- неизвестная таблица без записи данных.

Правила runtime workflow:

- сначала `workspace.open`, затем `runtime.ensure(mode="experiment")`;
- существующий runtime переиспользуется через `runtime.ensure`;
- `operation.wait` получает `timeout_s` не более 30 секунд;
- `runtime.close` не вызывается без явной необходимости;
- clean-generation test использует только явно обоснованный
  `runtime.restart`, а не закрытие service;
- вызовы не выполняются параллельно с EDT update той же файловой базы.

Symbolic CAPTURE не является обязательным. Он допускается только для common
modules после появления точного Designer-export, соответствующего загруженной
версии расширения, и согласованной пары project/source root. Текущий resolver
не используется для object modules data processors. Отсутствие CAPTURE не
блокирует ни одну acceptance criterion.

В конце разработки создаётся отдельный отчёт
`docs/research/<date>-metadata-provider-runtime-mcp-report.md`. Он содержит:

- точные места применения MCP и проверяемые гипотезы;
- выполненные tools/probes и результаты;
- ошибки с разделением источника: frontend, service, платформа или код задачи;
- полезные находки;
- потери времени, ограничения, ложные сигналы и вред persistent state;
- сравнение с EDT/YAxUnit и итоговую рекомендацию.

Пароли, tokens, process identifiers и бизнес-данные в отчёт не включаются.

## Перенос из старой ветки

Концептуально переиспользуются:

- объектный registry;
- private индекс providers по нормализованным сегментам;
- владение каталогом схемы стандартным provider-ом;
- adapter к существующему repeated provider исполняемых представлений;
- рекурсивная neutral conversion;
- lazy provider hierarchy.

Не переносятся:

- provider временных таблиц;
- provider-root UI;
- строковый marker вложенной таблицы как semantic type;
- пустая реализация параметров стандартных таблиц;
- создание provider/registry на каждый lookup;
- UI checklist без изменений форм;
- tool configuration и другие несвязанные файлы старой ветки.

Код переносится вручную небольшими slices после сверки с актуальным
`master`. Wholesale cherry-pick не используется.

## Риски и защита

- **Двойной каталог схемы.** Только стандартный provider владеет
  `ДоступныеТаблицы`; contexts используют registry.
- **Скрытый fallback.** При наличии registry старый lookup запрещён.
- **Повторный raw lookup.** `ОписаниеТаблицы()` вызывается напрямую без
  предварительного `ТаблицаСуществует()`.
- **Утечка platform object на клиент.** Form facade отображает neutral values
  в существующие columns и отбрасывает `ДанныеПоставщика`.
- **Сломанная join topology.** Все source traversals используют
  `ВсеИсточникиОператора()` и имеют test с join.
- **Загрязнение cache между запросами.** Один registry ограничен lifecycle
  верхнеуровневого запроса.
- **Ложный успех runtime probe.** Финальный gate всегда YAxUnit + EDT delta +
  ручная UI-проверка.
- **Stale extension в базе.** YAxUnit запускается только после подтверждённого
  incremental update нужного extension scope.

## Критерии готовности фазы semantics

- четыре новых объекта без `КОНС_` созданы и зарегистрированы;
- registry индекс неизменяем после инициализации и обнаруживает collisions;
- стандартные и executable tables возвращают neutral descriptions;
- вложенные поля и virtual parameters покрыты исполняемыми тестами;
- local sources не маршрутизируются через registry;
- nested-query и virtual-parameter contexts переиспользуют один registry;
- неизвестный именованный источник диагностируется независимо от обращения к
  полям;
- актуальная join topology сохранена;
- релевантные YAxUnit tests зелёные;
- EDT diagnostic delta проверен;
- runtime smoke выполнен либо gap явно зафиксирован с причиной.

## Критерии готовности фазы UI

- provider catalog contract реализован обоими providers;
- текущая иерархия и порядок корневых групп сохранены;
- все шесть callers переведены на server facade;
- model-local sources остаются локальными;
- form data не содержит `ДанныеПоставщика` и raw platform objects;
- UI YAxUnit/component tests зелёные;
- ручной сценарий формы пройден;
- подготовлен итоговый отчёт об использовании onec-runtime MCP;
- независимый reviewer не обнаружил незакрытых Critical/High findings.
