# Общий вызов функции и семантическая проверка сигнатур

**Статус:** проект для согласования; реализация не начата.
**Дата:** 2026-10-27.
**Выбранный пользователем подход:** единый `ВызовФункции` на всех этапах.

## Цель и границы

Убрать сигнатуры функций с обычным списком выражений из грамматики языка
запросов. Грамматика распознаёт имя, скобки, разделители и выражения;
семантический анализ проверяет существование функции, число и допустимость
аргументов, определяет результат и использование агрегатов.

Добавление обычной функции требует записи в каталоге семантики, без нового
правила грамматики, типа узла или обработчика каждого посетителя. Неизвестное
имя допускается синтаксическим разбором и отклоняется семантическим анализом.
Это не поддержка пользовательских функций и не разрешение исполнять
непроверенный вызов.

Функции с аргументами иной синтаксической категории сохраняют специальные
продукции. Общий parsergen остаётся универсальным: правила функций 1С не
добавляются в lowering, Parser IR или генераторы BSL/Python. Существующие
entrypoints и `lookahead = 2` сохраняются.

## Подтверждённое состояние

- `tools/parsergen/grammar/query-language.grammar` содержит 22 альтернативы
  `<Функция>`, четыре простых агрегата и особое правило `КОЛИЧЕСТВО`.
- Конструкторы находятся в `ЭлементыМоделиЗапроса`; обходчик диспетчеризует по
  строковому `Тип`. Семантический посетитель использует стек типов.
- Полный контракт посетителя задаёт `Шаблон_ПосетительМоделиВыражений`.
  Конкретные посетители: семантический, проверки применимости отбора и
  обработки разыменований для СКД. Генератор текста имеет свой диспетчер.
- `МодельЗапросаУтилиты` распознаёт агрегаты по виду узла и извлекает их
  аргумент при формировании псевдонимов; это также часть миграции.
- Фабрика базового узла сейчас не сохраняет переданный токен. Точные позиции
  новых семантических ошибок не входят в это изменение; сообщение содержит
  имя функции и, где применимо, номер аргумента.
- На момент исследования рабочее дерево чистое; локальный импорт parsergen
  подтверждён, `python -m parsergen validate --config parsergen.toml` завершён
  с кодом 0.

## Рассмотренные подходы

1. **Единый узел на всех этапах — выбран пользователем.** Все потребители
   переходят на общий контракт. Это требует согласованной миграции, зато
   устраняет зависимость формы дерева от сигнатур обычных функций.
2. **Общий синтаксический узел с последующим преобразованием в старые узлы.**
   Сохраняет часть существующих потребителей, но требует отдельного
   преобразования дерева и сохраняет специализированные контракты для
   каждой новой функции. Пользователь выбрал первый вариант.

## Грамматика и модель

Предлагаемая запись в существующем declarative DSL:

```text
<ВызовФункции> ::= @НовыйВызовФункции ИмяФункции = #ID_Функция '(' (Аргументы = <СписокВыражений>)? ')'
```

`НовыйВызовФункции` — новая предлагаемая фабрика со свойствами:

- `Тип = "ВызовФункции"`;
- `ИмяФункции` — исходное написание идентификатора;
- `Аргументы` — узел `СписокВыражений`, по умолчанию с пустыми `Элементы`.

Отсутствие списка внутри скобок оставляет коллекцию пустой. Поэтому `ГОД()`
разбирается синтаксически, а ошибка числа аргументов возникает в семантике.
Пустые элементы и завершающая запятая, например `ГОД(,)` и `ГОД(1,)`, остаются
синтаксическими ошибками.

`#ID_Функция` включает `ID` и существующие токены имён переносимых функций.
Это лексический класс, а не список разрешённых семантикой функций. Новое имя,
не зарезервированное лексером, уже имеет токен `ID` и не требует изменения
грамматики. Структурные ключевые слова и имена специальных форм в класс не
включаются. Существующие классы имён полей и псевдонимов сохраняются:
`ГОД`, `ГОД.Поле` и `ГОД(...)` различаются по контексту и просмотру двух
токенов. Корректность доказывается SELECT-анализом, а не порядком альтернатив.

## Какие функции переходят на общий узел

| Группа | Имена | Семантическое правило |
|---|---|---|
| Подстрока | `ПОДСТРОКА` | 3 аргумента, строка и числовые позиции; результат — строка |
| Части даты | `ГОД`, `КВАРТАЛ`, `МЕСЯЦ`, `ДЕНЬГОДА`, `ДЕНЬ`, `НЕДЕЛЯ`, `ДЕНЬНЕДЕЛИ`, `ЧАС`, `МИНУТА`, `СЕКУНДА` | 1 аргумент даты; результат — число |
| Замена NULL | `ЕСТЬNULL` | 2 аргумента; сохранить действующее объединение типов |
| Представления | `ПРЕДСТАВЛЕНИЕ`, `ПРЕДСТАВЛЕНИЕССЫЛКИ` | 1 аргумент; результат — строка; сохранить различия допустимых типов |
| Тип значения | `ТИПЗНАЧЕНИЯ` | 1 аргумент; результат — тип |
| Константа даты | `ДАТАВРЕМЯ` | 3 или 6 числовых констант; результат — дата |
| Обычные агрегаты | `СУММА`, `СРЕДНЕЕ`, `МИНИМУМ`, `МАКСИМУМ` | 1 аргумент; признак агрегата и действующие правила результата |

Ограничения, которые ранее обеспечивались синтаксисом `ДАТАВРЕМЯ`, переходят
в семантику: разбор произвольного выражения не делает его допустимым
аргументом этой функции. Проверка календарных значений также относится к
семантике. Новые функции и дополнительные языковые псевдонимы не добавляются.

В текущей грамматике `НЕДЕЛЯ` вызывает фабрику с именем `ДеньМесяца`.
В новой модели сохраняется фактическое имя `НЕДЕЛЯ`; оно не заменяется этим
именем фабрики при генерации текста.

## Исключения: отдельный синтаксис

| Форма | Причина отдельного правила |
|---|---|
| `ВЫРАЗИТЬ(выражение КАК тип)` | Ключевое слово `КАК` и описание типа |
| `ТИП(описание типа)` | Аргумент — описание типа, включая его параметры |
| `ЗНАЧЕНИЕ(путь)` | Путь метаданных/предопределённого значения, не поле источника |
| `НАЧАЛОПЕРИОДА`, `КОНЕЦПЕРИОДА`, `ДОБАВИТЬКДАТЕ`, `РАЗНОСТЬДАТ` | Идентификатор периода — особая категория аргумента |
| `КОЛИЧЕСТВО(...)` | Синтаксис `*` и `РАЗЛИЧНЫЕ` |

Для этих имён сохраняются существующие специализированные узлы и способы
обхода. Имена целиком исключаются из общего класса вызова: для
`КОЛИЧЕСТВО(Поле)` и `КОЛИЧЕСТВО(*)` не создаются конкурирующие ветви.
Проверки значений периода, типов и контекстной допустимости выполняются в
семантике; особая грамматика отвечает за форму аргументов. Обобщение этой
синтаксической категории или добавление других вариантов агрегатов сюда
не входит.

## Каталог и семантический анализ

Каталог описаний функций размещается в существующем
`МодельЗапросаУтилиты`, доступном на сервере и при внешнем соединении.
Новый общий модуль метаданных для этого не нужен. Данные каталога содержат
каноническое имя, допустимые количества аргументов, категорию
обычная/агрегатная, ограничения позиций и способ определения результата.
Конкретные имена новых методов и способ хранения каталога оставлены
реализатору; повторяющихся списков имён в посетителях быть не должно.

Поиск нечувствителен к регистру. Исходное написание хранится в AST,
семантика и генерация используют нормализованное каноническое имя известных
функций. Каталог не является динамическим реестром расширений и не исполняет
код по строковому имени.

Алгоритм обработки общего вызова:

1. При входе найти описание и проверить число аргументов до обхода детей.
   Неизвестная функция выдаёт понятную семантическую ошибку; ошибочная
   сигнатура не приводит к извлечению несуществующего элемента стека.
2. Обойти `Аргументы.Элементы` слева направо, по одному разу. Контейнер списка
   не посещается как самостоятельное выражение: нельзя свернуть несколько
   типов аргументов в тип обычного `СписокВыражений`.
3. При выходе извлечь ровно столько типов, сколько аргументов, восстановив
   исходный порядок, проверить ограничения и вывести тип результата.
4. Передать ожидаемые типы непосредственным параметрам запроса по действующему
   протоколу и обновить `ИспользуетсяАгрегатнаяФункция` для агрегатов.
5. Поместить один тип результата в стек. Форма узла остаётся `ВызовФункции`.

Проверки типов используют имеющуюся степень определённости модели: известный
несовместимый тип вызывает ошибку, неизвестный тип поля/параметра не является
сам по себе ошибкой. Сохраняется поддержка `NULL`, составных описаний типов и
объединения типов `ЕСТЬNULL`; новая система типов и полная проверка всех
контекстов SQL не создаются. Точные допустимые типы и календарные ограничения
фиксируются тестами и сверкой с 1С перед реализацией соответствующей проверки,
а не выводятся из названий фабрик.

Для исходной сверки EDT-MCP `validate_query` принял `ДАТАВРЕМЯ` с 3 и 6
числовыми аргументами, отклонил варианты с 1 и 4 аргументами и сообщил о
недостающем аргументе `ПОДСТРОКА("abc", 1)`. На варианте `ДАТАВРЕМЯ(&Год,1,2)`
сам валидатор вернул `Error executing EValidator`: это ограничение данной
проверки, а не подтверждённая диагностика платформы для параметра.

## Потребители и совместимость

- Добавить `ВызовФункцииПриВходе/ПриВыходе` в обходчик, полный шаблон и все
  три конкретных посетителя; обновить тестовый посетитель YAxUnit.
- Генератор текста печатает каноническое имя, скобки и элементы аргументов
  в исходном порядке. Он умеет работать до семантического анализа и сохраняет
  неизвестное имя, не выдавая его за проверенную функцию.
- Посетитель отбора сохраняет разрешение обычных функций флагом
  `ФункцииЯзыкаЗапросов` и допустимостью каждого аргумента; агрегаты остаются
  неделегируемыми. Количество снятых результатов равно числу аргументов.
- Посетитель СКД рекурсивно обрабатывает каждый аргумент, сохраняя замену полей
  и приведение ссылочных типов внутри вложенных вызовов.
- Утилиты группировки, сравнения и псевдонимов распознают агрегатность через
  описание функции и берут первый аргумент из общей коллекции; отдельная
  форма `КОЛИЧЕСТВО` продолжает поддерживаться.
- Обновить внутренние фабрики и проекции тестов. Удалять старые фабрики и
  callbacks только после поиска ссылок, включая формы и YAxUnit. Добавлять
  совместимые обёртки только при доказанном внешнем потребителе.
- Старые сравнительные тесты парсеров больше не требуют равенства видов узлов
  или стадии ошибки сигнатуры; вместо этого сравнивают смысл допустимого
  выражения. Неизменённые части модели остаются под прежними проверками.

## Проверка реализации

Разработка ведётся test-first, согласованными изменениями грамматики, модели
и потребителей. Минимальные значимые сценарии:

- неизвестное имя, пустой список, неправильная арность проходят синтаксис;
  семантика отклоняет их по соответствующей причине;
- вложенные вызовы, порядок аргументов, регистр, поле с именем функции,
  поле с разыменованием, параметры и ошибка разделителей;
- каждый переносимый вид функции: успешный результат и ошибочная сигнатура;
  известный несовместимый тип, неизвестный тип и `NULL`;
- `ДАТАВРЕМЯ`: 3/6 аргументов, прочая арность, нечисловая/неконстантная форма
  и недопустимая календарная дата;
- агрегатность, ограничения в отборах, генерация псевдонима и поведение
  `МИНИМУМ`/`МАКСИМУМ` для типа результата;
- все исключения сохраняют прежнюю форму; в том числе `ВЫРАЗИТЬ(... КАК
  ЧИСЛО(10,2))`, период и обе специальные формы `КОЛИЧЕСТВО`;
- цикл текст → AST → семантика → текст → AST сохраняет смысл; для неизвестного
  имени проверяется отдельный цикл без семантического анализа;
- посетители СКД и отбора корректно обрабатывают вложенные общие вызовы.

Команды запускаются с `PYTHONPATH=tools/parsergen/src` и UTF-8 stdout:

```text
python -m parsergen validate --config parsergen.toml
python -m parsergen generate --config parsergen.toml
python -m parsergen generate --config parsergen.toml --check
python -m pytest tools/parsergen/tests -q
git diff --check
```

Просмотреть все три сгенерированных артефакта и обновить соответствующие
fixtures `tools/parsergen/tests/fixtures/reference_parser/` точными файлами
генерации. Структурные метрики обновляются по фактическому результату.
Требуются отсутствие canonical SELECT-конфликтов при k=2 и детерминизм.
Ранее упоминавшийся `benchmarks/audit_migration.py` в текущем дереве отсутствует
и не является выполнимой проверкой этой задачи.

Запустить затронутые YAxUnit-модули парсера, модели выражений, семантики,
построения и генерации запросов и потребителей представлений через реально
обнаруженную конфигурацию запуска EDT. Ревалидировать все изменённые объекты
QueryConsoleZUP и тестовые модули yaxunit, отдельно сопоставив существующий
фон и новые диагностики. Полная перестройка и обновление ИБ не являются
автоматическими шагами; необходимость определяется реальной конфигурацией
запуска и изменениями.

Ручная завершающая проверка: открыть запрос с вложенной обычной функцией,
агрегатом и `ВЫРАЗИТЬ` в конструкторе; проверить отображение, редактирование,
обратную генерацию и понятную ошибку неправильной сигнатуры.

## Критерий готовности

Обычный вызов имеет единый AST до и после семантики, сигнатуры отсутствуют
в его грамматике, семантические ошибки покрыты тестами, все потребители
обновлены согласованно, специальные формы сохранены. Итог содержит список
файлов, фактические проверки, оставшиеся диагностики и результат ручного
сценария. До согласования этого документа производственный код не меняется.
