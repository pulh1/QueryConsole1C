# Ленивое разрешение метаданных таблиц в семантике

Дата: 2026-08-31

Статус: утверждённый дизайн, ожидает просмотра письменной спецификации

## Место в архитектуре

Эта спецификация уточняет semantic hot path из
`2026-08-30-metadata-provider-semantics-ui-design.md`. Она заменяет части
исходного дизайна, где semantic consumers получают полное
`ОписаниеТаблицы`, positive cache полных описаний считается основным semantic
cache, а legacy context допускает прямой lookup без реестра. Границы реестра,
временных таблиц, вложенных запросов и будущей UI-фазы не меняются.

Уже принятые архитектурные инварианты сохраняются:

- semantic context хранит реестр, но не `ДоступныеТаблицыИБ` и не отдельную
  `СхемаЗапроса`;
- один standard provider создаёт одну `СхемаЗапроса` на корневой разбор;
- canonical semantic contexts не имеют legacy fallback при отсутствии реестра;
- маршрутизация standard provider-а использует статический platform superset
  из 19 первых сегментов и не обходит `ДоступныеТаблицы` при инициализации.

## Причина изменения

Первый полный runtime benchmark обнаружил два разных источника
стоимости:

1. Рекурсивный обход всего `СхемаЗапроса.ДоступныеТаблицы` при
   инициализации давал около 5,9–6,0 с на semantic corpus. Обход уже
   заменён статическим platform superset из 19 первых сегментов.
2. После этого исправления feature остаётся на уровне 319–336 мс
   против 14,25 мс у прогретого baseline. Semantic path вызывает
   `ОписаниеТаблицы`, а конкретный provider рекурсивно преобразует
   все поля, вложенные таблицы и параметры, хотя caller использует
   одно поле или только классификацию источника.

Read-only trace подтвердил:

- `СемантическийАнализВыраженийУтилиты` использует только одно поле;
- `ПостроительМоделиЗапроса` использует факт существования, `ВидИсточника`
  и raw-описание только для исполняемого представления;
- `ОбработкаПредставлениеЗапросов` использует `ВидИсточника` и raw-описание;
- выражение `ВсеПоляИсточника` не раскрывает полный каталог в
  semantic visitor.

Следовательно, semantic hot path не должен вызывать
`ОписаниеТаблицы`.

## Решение

### Dynamic contract provider-а

Контракт semantic-фазы расширяется двумя точечными операциями:

```text
Инициализировать()
ИмяПоставщика()
Сегменты()
ТаблицаСуществует(ИмяТаблицы)
НайтиТаблицу(ИмяТаблицы)
НайтиПоле(ИмяТаблицы, ИмяПоля)
ОписаниеТаблицы(ИмяТаблицы)
```

`НайтиТаблицу()` возвращает `Неопределено` или лёгкое описание:

```text
ИмяТаблицы
ИмяПоставщика
ВидИсточника
Представление
ДанныеПоставщика
```

В нём нет `Поля` и `Параметры`. `ДанныеПоставщика` остаётся opaque
server-only значением. Для стандартной таблицы это platform object
конкретной таблицы, для исполняемого представления — его
существующее raw-описание.

`НайтиПоле()` возвращает `Неопределено` или нейтральное описание
только запрошенного поля. Оно не строит полное описание
таблицы. Если найдено обычное поле, конвертируется только оно.
Если найдена вложенная таблица, конвертируется только её
ветвь с дочерними полями, а не все поля родительской таблицы.

`ОписаниеТаблицы()` сохраняет текущий полный контракт. Он нужен
для явного раскрытия в UI и для consumers, которым действительно
нужны все поля и параметры. Он не вызывается в semantic hot path.

### Реестр

Реестр добавляет `НайтиТаблицу()` и `НайтиПоле()`. Каждая операция
один раз выбирает provider по первому сегменту и сразу делегирует
вызов. Реестр не вызывает `ТаблицаСуществует()` перед делегированием
и не владеет provider caches.

### Конкретные provider-ы

Стандартный provider:

- один раз создаёт `СхемаЗапроса` при инициализации;
- ищет таблицу через `ДоступныеТаблицы.Найти()` без обхода каталога;
- `НайтиТаблицу()` строит только лёгкое описание;
- `НайтиПоле()` вызывает `Поля.Найти()` и конвертирует только найденное
  поле или вложенную ветвь;
- `ОписаниеТаблицы()` сохраняет полную рекурсивную конверсию для UI.

Provider исполняемых представлений:

- `НайтиТаблицу()` получает raw-описание через существующий
  `ПоставщикИсполняемыхПредставлений` и не конвертирует поля и параметры;
- `НайтиПоле()` использует raw-индекс `ПоляПоИменам` и конвертирует только
  найденное поле;
- `ОписаниеТаблицы()` сохраняет полную конверсию для UI.

## Caches и lifecycle

Все caches остаются в конкретном provider-е. Реестр не кэширует
описания.

Каждый provider хранит только нужные ему независимые positive caches:

- лёгкие описания по нормализованному имени таблицы;
- точечные описания по паре нормализованных имён таблицы и поля;
- полные описания по нормализованному имени таблицы.

Если конкретная операция дешева и повторное преобразование отсутствует,
соответствующий cache можно не создавать. Наличие cache не является частью
публичного контракта provider-а.

Неизвестные таблицы и поля не кэшируются. Один корневой semantic
разбор владеет одним реестром, каждым его provider-ом, их caches и одной
схемой стандартного provider-а. Derived contexts переиспользуют тот же
реестр. Между независимыми корневыми разборами provider objects и caches
не разделяются.

## Миграция consumers

- `СемантическийАнализВыраженийУтилиты` заменяет
  `Реестр.ОписаниеТаблицы()` и поиск в готовом массиве на
  `Реестр.НайтиПоле()`.
- `ПостроительМоделиЗапроса` и `ОбработкаПредставлениеЗапросов` заменяют
  `ОписаниеТаблицы()` на `НайтиТаблицу()`. Ошибки неизвестной таблицы,
  классификация `ВидИсточника` и передача `ДанныеПоставщика` не меняются.
- Прямых вызовов `ОписаниеТаблицы()` в semantic hot path после миграции
  не остаётся.

Локальные источники — временные таблицы, вложенные запросы, таблицы
значений и aliases — продолжают разрешаться до реестра.

## Ошибки и границы

- Unknown segment, table и field возвращают `Неопределено` на уровне
  registry/provider.
- User-facing исключения формируют те же consumers, что и сейчас.
- Отрицательные caches не вводятся.
- Глобальный provider или cache между корневыми разборами не вводится.
- UI-иерархия и transport DTO в эту правку не входят.
- Lexer, parser, AST и runtime MCP не меняются.

## Проверка

### TDD-контракты

1. Registry spy доказывает прямую делегацию `НайтиТаблицу()` и
   `НайтиПоле()` без вызова `ОписаниеТаблицы()`.
2. Реальный standard provider находит обычное и вложенное поле без
   предварительного полного описания.
3. Реальный executable provider находит поле через raw-индекс.
4. Builder и full semantic tests сохраняют standard, executable, unknown,
   temporary, nested, table-value и join behavior.
5. Отдельный test доказывает, что semantic consumer не вызывает полную
   конверсию. Это observable call contract spy provider-а, а не поиск строки
   в production source.

### Performance gate

Перед timed series каждая ревизия получает отдельный excluded
из статистики preconditioning run после загрузки extension. Затем выполняется
новая A–B–B–A серия с теми же корпусами, 3 warmups, 20 samples и
batch target 25 мс. Перед каждым timed run debugger, targets, breakpoints,
`dbgs` и port 1550 должны быть нулевыми.

Правка не принимается, если после предварительного прогрева:

- feature median per call на `semantic_contract` превышает baseline более чем
  на 25%;
- feature median per call на `repeated_standard_source` превышает baseline
  более чем на 25%;
- feature p95 per call любого корпуса превышает baseline более чем
  на 50%.

При сильном order effect серия не даёт успешный verdict и повторяется
с симметричным preconditioning.

## Не входит в изменение

- раскрытие UI-дерева и transport DTO;
- полное ленивое раскрытие дочерних полей внутри уже выбранной
  вложенной таблицы;
- global/session cache provider objects;
- negative cache;
- изменение parser, AST и модели выражений;
- изменение существующего `ПоставщикИсполняемыхПредставлений`.
