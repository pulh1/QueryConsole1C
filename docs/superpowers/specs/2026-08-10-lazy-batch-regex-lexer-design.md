# Lazy materialization batch-regex lexer языка запросов 1С

## Статус и цель

Документ задаёт минимальный рефакторинг production lexer
`DataProcessor.ЛексическийАнализатор`: batch-regex recognition сохраняется,
но полная предварительная materialization значимых токенов заменяется
последовательной materialization по запросам `СледующийТокен()`.

Parser продолжает использовать существующий streaming-контракт и собственный
двухтокенный lookahead. Изменения grammar, parser, AST/model semantics и
performance tuning находятся вне scope.

## Подтверждённое исходное состояние

Текущий production lexer хранит одновременно:

- исходный текст;
- массив regex matches, локальный для установки текста;
- массив полноценных `Токен[]` на весь запрос;
- индекс следующего токена;
- отложенную лексическую ошибку;
- позицию EOF.

`УстановитьОбрабатываемыйТекст()` выполняет два batch-вызова
`СтрНайтиВсеПоРегулярномуВыражению()`: основной scan lexical units и отдельный
scan переводов строк. Затем метод проверяет coverage, классифицирует каждый
значимый match, преобразует literal values и сохраняет все структуры токенов.

Generated parser использует публичные методы `Инициализировать()`,
`УстановитьОбрабатываемыйТекст()` и `СледующийТокен()`. Адаптация parser к lazy
materialization не требуется.

Исторический lexer подтверждает, что после `#` допустим любой символ из полного
множества продолжения identifier, включая цифру. Текущий batch-regex и тест
`ЦифраПослеРешеткиОтклоняется` ошибочно сделали это правило строже. В рамках
рефакторинга восстанавливается legacy-совместимость `#1` без изменения
поведения одиночного `#` и `#` перед неизвестным символом.

## Выбранный дизайн

### Состояние модуля

После установки текста lexer хранит:

- `ИсходныйТекст`;
- `Совпадения` основного batch regex scan;
- `ИндексСледующегоСовпадения`;
- `ОжидаемаяПозиция` для contiguous coverage;
- `ПереводыСтрок` отдельного batch scan;
- одно монотонное `СостояниеПозиции`;
- `ПозицияEOF`.

Полный массив `Токен[]`, индекс токена и отложенная ошибка удаляются. Lexer не
хранит ссылку на уже возвращённый token.

### Установка текста

`УстановитьОбрабатываемыйТекст()`:

1. сохраняет исходный текст;
2. одним вызовом получает все lexical matches;
3. отдельным существующим вызовом получает переводы строк;
4. устанавливает match cursor и ожидаемую абсолютную позицию в начало текста;
5. создаёт начальное состояние source position;
6. вычисляет совместимую позицию EOF.

Метод не классифицирует lexical matches, не преобразует literals, не создаёт
значимые tokens и не проверяет будущие gaps. Поэтому lexical error в хвосте не
может проявиться во время установки текста.

### Последовательное чтение

`СледующийТокен()` выполняет явный цикл по `Match[]`:

1. читает match по текущему индексу;
2. сравнивает его начало с `ОжидаемаяПозиция`;
3. при gap формирует совместимую ошибку в ожидаемой позиции;
4. для whitespace или `//` comment продвигает cursor и coverage state без
   создания token и продолжает цикл;
5. для значимого match вычисляет source position, классифицирует match,
   создаёт один token, продвигает cursor и возвращает token;
6. после исчерпания matches проверяет непокрытый хвост и возвращает EOF.

Trivia пропускается lazily. Block comments не добавляются.

### Ошибки и повторные вызовы

Отдельная отложенная ошибка больше не нужна: классификация выполняется именно
при запросе очередного token. При gap или ошибке преобразования lexer не
продвигает significant match cursor. Поэтому повторный вызов
`СледующийТокен()` снова выдаёт то же исключение в той же позиции.

Для trivia cursor продвигается только после успешной проверки coverage. Для
значимого match cursor и `ОжидаемаяПозиция` продвигаются только после успешной
materialization. Непокрытый tail также остаётся воспроизводимой ошибкой.

### Source positions и EOF

Отдельный regex scan `\r\n|\r|\n` сохраняется. `ПозицияИсточника()` использует
одно состояние с индексом перевода строки, номером строки и абсолютным началом
строки. Состояние движется только вперёд вместе с match cursor; повторный поиск
от начала текста не выполняется.

Whitespace, comments и multiline strings могут содержать переводы строк. Их
не требуется обходить посимвольно: при запросе позиции следующего значимого
token функция догоняет нужную абсолютную позицию по массиву переводов.

EOF остаётся структурой token с неопределёнными классом, типом и лексемой и с
координатой сразу после исходного текста. Повторные вызовы после EOF возвращают
observable-эквивалентные EOF tokens.

## Regex и lexical semantics

Составной читаемый regex сохраняется. Меняется только фрагмент временного
identifier: после `#` требуется один или более символов из полного множества
identifier continuation, включая цифры. Одиночный `#` остаётся gap и получает
диагностику `Некорректный идентификатор с #`.

Без изменений сохраняются:

- whitespace, включая неразрывный пробел;
- однострочные `//` comments;
- escaped quotes и multiline strings;
- числовые формы `123`, `123.45`, `123.` и `.45`;
- keywords и обычные identifiers;
- одно- и многосимвольные lexemes;
- token classes, types, lexemes и literal values;
- CR, LF и CRLF source positions;
- сообщения и timing lexical errors.

## Проверки

Реализация выполняется через RED/GREEN:

1. обновляется regression test для legacy-compatible `#1` и сохраняются
   negative cases `#` и `#@`;
2. добавляется явный тест установки текста с корректным далёким префиксом и
   lexical error в хвосте: установка и чтение префикса успешны, ошибка возникает
   только при достижении cursor;
3. существующий тест повторной ошибки подтверждает, что cursor не перескакивает
   ошибочный участок;
4. differential tests сравнивают класс, тип, лексему, значение и координаты;
5. выполняются lexer, parser и parser-query suites;
6. EDT revalidation и diagnostics проверяются только для затронутых объектов.

Архитектурное отсутствие `Token[]` дополнительно проверяется code review:
production state не содержит `Токены`, а `УстановитьОбрабатываемыйТекст()` не
вызывает token constructors или literal conversion. Публичный test-only API
для introspection внутреннего состояния не добавляется.

Performance benchmarks, profiler и parser performance diagnostics намеренно
не запускаются.

## Alternatives

### Сохранить отложенную ошибку

Совместимо, но после переноса classification в `СледующийТокен()` состояние
становится избыточным. Ошибка естественно возникает в нужный момент, а
непродвинутый cursor обеспечивает повторяемость.

### Iterator или coroutine abstraction

Не выбрано: добавляет framework и косвенное управление состоянием без пользы
для модели `Match[] + integer cursor`.

### Ленивый regex recognition

Не выбрано: нарушает основную batch-regex architecture. Ленивой является
только classification/materialization, а `FindAll` по всему тексту остаётся.

## Риски и ограничения

- Ошибочное продвижение cursor до materialization может сделать повторный
  вызов после исключения несовместимым; порядок обновления state защищается
  тестом.
- Source position state является монотонным, поэтому позиция вычисляется до
  изменения cursor, но не должна вычисляться для более позднего участка после
  ошибки.
- Массив regex matches остаётся полностью в памяти; его оптимизация является
  отдельной задачей.
- Ранее полученные runtime measurements выполнялись конфигурацией EDT с
  `ATTR_SHOW_PERFORMANCE=true`; они не используются как доказательство в этой
  задаче и требуют отдельного чистого повторного измерения позже.
