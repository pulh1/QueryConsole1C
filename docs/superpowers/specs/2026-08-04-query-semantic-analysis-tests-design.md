# Тесты семантического анализа выражений запросов

Дата: 2026-08-04

Статус: готово к реализации

## Контекст

После лексера и парсера QueryConsoleZUP выполняет отдельный этап семантического
обогащения AST. Этот этап выводит тип выражения, разрешает источники и поля,
собирает параметры запроса и выставляет признаки агрегатов и внешних
источников. В ближайших задачах грамматика и форма AST будут существенно
перерабатываться, включая поддержку левой рекурсии. Поэтому семантические
тесты не должны зависеть от текущей топологии дерева рекурсивного спуска.

Основной публичный контракт находится в
`CommonModules/ОбработкаМоделиЗапроса/Module.bsl`:

- `ОбработатьВыражение(Выражение, Контекст, РассчитываемыеСвойства,
  Посетитель = Неопределено)` на строках 772–781;
- `ОбработатьВыражениеУсловие` на строках 645–659;
- `ОбработатьВыражениеВыбираемогоПоля` на строках 783–791;
- `ОбработатьМодельЗапроса` на строках 114–152 для полного пакета.

`ОбработатьВыражение` создаёт
`Обработки.СемантическийАнализВыраженийПосетитель`, передаёт AST в
`ОбходМоделиЯзыкаВыражений.ОбойтиДерево` и записывает итог в переданный
контейнер вычисляемых свойств. Прямое тестирование callback-методов visitor не
является публичным контрактом.

## Цели

1. Зафиксировать публично наблюдаемый результат семантической обработки
   корректных выражений независимо от реализации parser и visitor.
2. Покрыть вывод типов, ограничения параметров, разрешение полей и источников,
   агрегатные признаки и семантические ошибки.
3. Разделить быстрые тесты на объектах в памяти, проверки synthetic sources,
   metadata-backed проверки и минимальный parser-to-semantic handshake.
4. Сохранить основной YAxUnit-набор зелёным, а доказанные дефекты и будущие
   правила разместить в отдельном opt-in RED-наборе.
5. Создать явную матрицу покрытия 59 callback-методов visitor и значимых ветвей
   `СемантическийАнализВыраженийУтилиты`.

## Не входит в работу

- изменение production-парсера, visitor, model factories или утилит;
- исправление найденных семантических дефектов;
- выполнение запросов и чтение или запись прикладных данных;
- UI-тесты и замена существующих Vanessa Automation сценариев;
- фиксация порядка callback-вызовов, состояния стека visitor или текущей
  рекурсивной топологии AST;
- выбор ещё не согласованной политики совместимости операндов и разрешения
  конфликтующих ограничений одного параметра.

## Подтверждённый production-контракт

### Input AST

Входные узлы создаются публичными функциями
`ЭлементыМоделиЗапроса.Новый*`. Для semantic unit/component tests это именно
fixture builders, а не источник ожидаемых результатов. Например:

- `НовыйКонстанта`, `НовыйПараметрЗапроса`, `НовыйБинарнаяОперация`;
- `НовыйРазыменование`, `НовыйПолеИсточника`;
- `НовыйПриведениеТипа`, `НовыйВыбор`, агрегаты и встроенные функции;
- `НовыйИсточник`, `НовыйИсточникДанныхТаблица`,
  `НовыйИсточникДанныхВременнаяТаблица`,
  `НовыйИсточникДанныхВложенныйЗапрос`.

`НовыйИсточникДанныхВложенныйЗапрос` применяется только для вложенного
источника секции `ИЗ`. Узел вложенного запроса справа от `ОператорВ.Список`
имеет тип `ЗапросВыбора` и создаётся непосредственно через
`НовыйЗапросВыбора()` с заполненным массивом `Операторы`.

Тесты не разбирают строку parser-ом для построения обычной semantic fixture.
Так изменение грамматики не приводит к массовым ложным падениям тестов
семантики.

### Output contract

Контейнер результата создаётся через
`ЭлементыМоделиЗапроса.НовыйВыражениеМоделиЗапроса` на строках 574–601 и
содержит:

- `ТипЗначения` — `ОписаниеТипов`;
- `ИспользуетсяАгрегатнаяФункция` — `Булево`;
- `ПоляИсточников` — `Соответствие`;
- `ПараметрыЗапроса` — `Соответствие` описаний параметров;
- `ИспользуютсяИсточникиВнешнегоЗапроса` — `Булево`.

Описание параметра создаётся функцией `НовыйОписаниеПараметраЗапроса` на
строках 890–906 и содержит `Имя`, `ТипЗначения` и `ЭтоСписокЗначений`.

Семантический проход заменяет первый элемент разыменования на
`ПолеИсточника` и записывает `ИдентификаторИсточника`. Безопасный зелёный
source case передаёт каноническое имя `ИНН` и ожидает `ИНН` в
`ПолеИсточника.ИмяПоля` и значении `ПоляИсточников`; ключ карты имеет вид
`<идентификатор>.ИНН`. Поведение при отличающемся регистре не является
зелёным контрактом и остаётся только decision gate. Отдельной таблицы символов
и отдельной коллекции диагностик нет. Ошибки возвращаются исключениями.

### Visitor chain

Цепочка имеет следующий вид:

```text
ОбработкаМоделиЗапроса.ОбработатьВыражение
  → СемантическийАнализВыраженийПосетитель.СоздатьПосетитель
  → ОбходМоделиЯзыкаВыражений.ОбойтиДерево
  → ...ПриВходе / ...ПриВыходе
  → ЗавершитьОбходВыражения
  → РассчитываемыеСвойства.ТипЗначения
```

`ОбходМоделиЯзыкаВыражений` содержит 30 node dispatchers. Object module
visitor содержит 64 метода; методы 4–62 образуют 59 callback-методов.
Coverage matrix перечисляет каждый callback отдельно, включая отдельную строку
`ПосетитьВложенныйЗапрос`. Для неё используется самостоятельный synthetic case
узла `НовыйЗапросВыбора()` с непустым `Операторы` справа от `В`; внешний
оператор `В` получает вторую, отдельную строку покрытия.

## Архитектура тестов

### 1. Pure semantic component tests

AST строится model factories. Для выражений без разыменования передаётся
пустая `Структура` вместо полного production-контекста. Это изолирует:

- константы и параметры;
- арифметику, сравнения и логические операции;
- списки, casts и `CASE`;
- агрегаты;
- функции, не использующие metadata.

Каждый case получает новый AST, новый контейнер результата и новый context.
Дорожка размещается в common module `КОНС_ОМ_ОбработкаМоделиЗапроса` и
именованном YAxUnit-наборе `СемантикаЧистыеВыражения`.

### 2. Synthetic-source component tests

Источники, колонки вложенного запроса и описания временных таблиц строятся в
памяти через model factories. Fixture получает полный публичный контекст через
`ОбработкаМоделиЗапроса.КонтекстОбработкиВыражения()`, после чего очищает и
контролируемо заполняет:

- `ИспользуемыеТаблицы`;
- `ИсточникиПоИдентификаторам`;
- `ИдентификаторыИсточниковВнешнегоЗапроса`;
- `ОписанияВременныхТаблиц`;
- флаги доступности aliases и внешних источников.

При этом сохраняются обязательные для `ПосетитьВложенныйЗапрос` свойства
`ИндексЗапросаПакета`, `ДоступныеТаблицыИБ`, `ОписанияВременныхТаблиц` и
`__СхемаЗапрос`. Fixture не разбирает полный запрос и не использует
прикладные данные.

Эти тесты покрывают поиск явного alias, однозначный и неоднозначный
unqualified field, nested-query columns, in-memory temporary tables и флаг
внешнего источника без зависимости от данных ИБ.
Дорожка размещается в common module
`КОНС_ОМ_ОбработкаМоделиЗапросаИсточники` и именованном YAxUnit-наборе
`СемантикаСинтетическиеИсточники`.

### 3. Metadata-backed component tests

Используется `ОбработкаМоделиЗапроса.КонтекстОбработкиВыражения`, который
создаёт `СхемаЗапроса` и `ДоступныеТаблицыИБ`. Глобальные `Метаданные` и
`СхемаЗапроса` не мокируются.

Минимальная стабильная fixture — `Справочник.Организации`, подтверждённый в
EDT-проекте базовой конфигурации:

- `Ссылка` → `СправочникСсылка.Организации`;
- `ИНН` → `Строка`;
- `ЕстьОбособленныеПодразделения` → `Булево`;
- `ГоловнаяОрганизация` → `СправочникСсылка.Организации`;
- `ГоловнаяОрганизация.ИНН` → `Строка`.

Тесты используют только metadata и не создают, не читают и не изменяют
элементы справочника.
Дорожка размещается в common module
`КОНС_ОМ_ОбработкаМоделиЗапросаМетаданные` и именованном YAxUnit-наборе
`СемантикаМетаданные`.

### 4. Parser-to-semantic handshake

Небольшой отдельный пакет вызывает `ОбработкаМоделиЗапроса.РазобратьЗапрос`
для нескольких коротких запросов. Он доказывает совместимость parser AST и
semantic visitor, но не дублирует parser matrix и не становится основным
источником semantic coverage.

Дорожка размещается в common module
`КОНС_ОМ_ОбработкаМоделиЗапросаИнтеграция` и именованном YAxUnit-наборе
`СемантикаИнтеграцияПарсер`.

При регенерации parser этот пакет может потребовать адаптации к новому
публичному AST. Pure и synthetic semantic assertions при этом должны остаться
без изменений либо выявить реальное изменение semantic contract.

## Устойчивые assertions

Основной зелёный набор проверяет только наблюдаемый контракт:

- множество типов результата: количество `Типы()` и `СодержитТип` для каждого
  ожидаемого типа;
- имя параметра, множество его типов и `ЭтоСписокЗначений`;
- `ИдентификаторИсточника`, совпадающий с идентификатором разрешённого
  источника;
- для source fixture с каноническим входом `ИНН`: `ИмяПоля = "ИНН"` и
  `ПоляИсточников["<идентификатор>.ИНН"] = "ИНН"`;
- признаки агрегата и внешнего источника;
- смысловой фрагмент сообщения исключения;
- независимость повторных вызовов.

Не проверяются:

- строковое представление или порядок типов в `ОписаниеТипов`;
- внутренний marker произвольного типа как самостоятельный бизнес-контракт;
- порядок обхода и вызовов visitor;
- конкретная форма бинарного дерева при длинных цепочках;
- внутренние token coordinates parser в semantic-only тестах.

Для текущего arbitrary marker тест проверяет
`МодельЗапросаТипы.СодержитПроизвольныйТип`, а не жёстко фиксирует, что marker
реализован типом `Массив`.

## Зелёная матрица

Оценка относится к matrix cases, а не к числу YAxUnit procedures.
Параметризованный тест может закрывать несколько строк.

| Пакет | Cases |
|---|---:|
| Pure constants, parameters и operations, включая первый vertical slice | 34–40 |
| Operators, lists, casts и `CASE` | 18–22 |
| Aggregates и built-ins | 26–32 |
| Synthetic sources, dereference, VT и subquery | 18–24 |
| Metadata-backed field/reference resolution | 10–14 |
| Semantic errors | 8–12 |
| Parser-to-semantic handshake | 8–12 |
| **Итого** | **122–156** |

Первый vertical slice содержит 12 cases:

1. четыре primitive constants;
2. standalone parameter с arbitrary marker;
3. вывод типа параметра из арифметики;
4. Boolean result сравнения;
5. Boolean result логической операции и вывод типа параметра;
6. explicit primitive cast;
7. union типов `CASE`;
8. `МИНИМУМ` с сохранением типа аргумента;
9. `СУММА` с числовым результатом и aggregate flag.

Четыре primitive constants выполняются одним параметризованным тестом, поэтому
суммарно получается 12 matrix cases. Стабильные ошибки и независимость
повторных вызовов добавляются в следующих пакетах.

## Opt-in RED: будущая семантика

Отдельный common module регистрирует тесты только при явном module filter,
аналогично `КОНС_Обр_ПарсерБудущаяГрамматика_МО`. Общий прогон его не
регистрирует.

Доказанные текущим кодом, но не исправляемые этой задачей gaps:

1. `%` парсится, но semantic visitor направляет его в логическую ветвь вместо
   числовой операции.
2. Parser создаёт `ФункцияПодстрока`, но expression walker не имеет dispatcher
   этого типа.
3. Date-part functions возвращают число, но неверный вызов helper не выводит
   тип `Дата` для параметра.
4. `*` не образует консистентный semantic result.
5. `Источник.*` не образует консистентный semantic result.

Эти пять acceptance cases имеют однозначный внешний результат и могут быть
сразу записаны как opt-in RED без production-изменений.

### Decision gate: канонизация имени поля

Зелёный контракт использует только канонический вход `ИНН` и ничего не
утверждает о mixed-case вариантах. До добавления такого case необходимо
выбрать и зафиксировать политику:

- preserve: `ИмяПоля` сохраняет пользовательское написание;
- canonicalize: `ИмяПоля` заменяется именем поля из источника/metadata.

До решения возможный case с различающимся регистром имеет статус
`decision_required`; он не входит ни в зелёный, ни в исполняемый RED-набор.

### Decision gate: совместимость операндов

До добавления executable acceptance cases необходимо выбрать одну политику:

- strict: несовместимые типы арифметики, сравнения и non-Boolean условия
  `CASE` вызывают semantic error;
- compatibility: сохраняется текущее permissive поведение для поддерживаемых
  операций.

### Decision gate: конфликт ограничений параметра

До добавления executable acceptance case необходимо выбрать результат
несовместимых usages одного параметра:

- semantic error;
- union допустимых типов;
- сохранение arbitrary type с отдельной диагностикой или без неё.

До решения строки всех трёх gate находятся в coverage matrix со статусом
`decision_required` и не регистрируются ни в зелёном, ни в RED-наборе.

## Ошибки в зелёном наборе

Характеризуются только уже однозначные и полезные проверки:

- логический оператор с заведомо не-Boolean операндом;
- условие запроса не-Boolean типа;
- отсутствующее и неоднозначное поле synthetic source;
- неизвестный source alias;
- невозможное разыменование нессылочного типа;
- неизвестный reference type в cast/`ЗНАЧЕНИЕ`;
- unsupported AST node;
- недопустимый list type для выбираемого поля.

Проверяется смысловая часть сообщения, а не полный platform stack trace.

## Incremental-only workflow

Все YAxUnit-запуски обязаны использовать:

```text
updateBeforeLaunch=true
updateScope="extension:yaxunit"
```

Запрещены:

- `clean_project`;
- full rebuild;
- update scope `all`;
- обновление всей конфигурации или обоих расширений без отдельной причины;
- production-правки внутри этого test plan.

Сначала запускается один preflight smoke, затем тесты добавляются пакетами и
запускаются точным `modules=[...]` фильтром. Четыре зелёные дорожки имеют
независимые фильтры:

```text
modules=["КОНС_ОМ_ОбработкаМоделиЗапроса"]
modules=["КОНС_ОМ_ОбработкаМоделиЗапросаИсточники"]
modules=["КОНС_ОМ_ОбработкаМоделиЗапросаМетаданные"]
modules=["КОНС_ОМ_ОбработкаМоделиЗапросаИнтеграция"]
```

Каждый вызов также передаёт `extensions=["YAXUNIT"]`,
`updateBeforeLaunch=true` и `updateScope="extension:yaxunit"`. Opt-in RED
запускается только точным module filter и никогда не входит в зелёные прогоны.

Если зелёный characterization case обнаруживает новый production defect,
исполнитель сохраняет доказательство, прекращает задачу и запрашивает решение.
Он не исправляет production-код и не ослабляет assertion.

### Узкая граница статической диагностики EDT для Task 1

EDT-проект `yaxunit` не моделирует публичные symbols соседнего расширения
`QueryConsoleZUP`, хотя runtime infobase их компилирует и выполняет. Для первого
smoke-модуля независимо подтверждены ровно три ложных `undefined-variable`:

| File:line | Check | Exact message |
|---|---|---|
| `CommonModules/КОНС_ОМ_ОбработкаМоделиЗапроса/Module.bsl:25` | `undefined-variable` | `Переменная 'ЭлементыМоделиЗапроса' не определена [Сервер]` |
| `CommonModules/КОНС_ОМ_ОбработкаМоделиЗапроса/Module.bsl:34` | `undefined-variable` | `Переменная 'ЭлементыМоделиЗапроса' не определена [Сервер]` |
| `CommonModules/КОНС_ОМ_ОбработкаМоделиЗапроса/Module.bsl:36` | `undefined-variable` | `Переменная 'ОбработкаМоделиЗапроса' не определена [Сервер]` |

Это не общий allowlist. Task 1 может принять только эти три markers, если
одновременно: identities/lines/count совпадают; весь diagnostic delta изолирован
новым модулем и не содержит иных `ERROR/CRITICAL/MAJOR`; точный smoke 1/1 реально
исполняет все три ссылки; metadata registration и server flags проверены. Любое
изменение identity, позиции или количества либо падение smoke снова закрывает
gate и требует отдельного review. Следующие пакеты не наследуют исключение
автоматически.

## Риски при изменении grammar/AST

- Новый parser может переименовать node types или поля. Тогда нужен явный
  compatibility adapter либо согласованное изменение model contract; нельзя
  переписывать semantic expectations под случайную новую topology.
- Левая рекурсия меняет grouping AST, но не должна менять type set, parameter
  constraints, resolved field identity и semantic flags.
- Изменение marker произвольного типа не должно ломать тесты, использующие
  `СодержитПроизвольныйТип`.
- Metadata-backed tests зависят от базовой конфигурации, поэтому используют
  один небольшой проверенный объект, а не широкий список ZUP metadata.
- `ПоставщикИсполняемыхПредставлений` нельзя мокировать штатным Мокито для
  методов расширения; его ветви не входят в первый scope без дополнительного
  read-only аудита `Описание()`.

## Критерии готовности

- runtime preflight доказывает доступность model factories и
  `ОбработатьВыражение` из `yaxunit`;
- зелёная матрица содержит 122–156 cases и закрывает все 59 callbacks либо
  документирует ветвь как opt-in RED, decision gate или out of scope;
- pure, synthetic-source, metadata-backed и handshake пакеты запускаются
  независимо;
- metadata tests не читают и не записывают данные;
- все четыре зелёных semantic modules проходят отдельно;
- opt-in module воспроизводит пять заранее доказанных RED-gap;
- ни один production-файл не изменён;
- все обновления выполнялись только с `updateScope="extension:yaxunit"`;
- независимый reviewer проверил coverage matrix, устойчивость assertions и
  отсутствие зависимости от parser topology.
