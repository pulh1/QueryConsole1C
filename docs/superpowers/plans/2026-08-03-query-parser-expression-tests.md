# Query Parser Expression Tests Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Покрыть зелёными black-box YAxUnit-тестами публичный контракт `Обработки.Парсер.РазобратьВыражение` без закрепления праворекурсивной формы длинных цепочек операторов.

**Architecture:** Все тесты и приватные assertion-helper методы добавляются в существующий серверный общий модуль `КОНС_Обр_Парсер_МО` проекта `yaxunit`. Каждый пакет сначала регистрирует одну намеренно падающую RED-заглушку, затем одной guarded-записью заменяет её полным набором параметризованных тестов и выполняет один GREEN-прогон всего модуля. Производственный парсер и модель выражений не изменяются.

**Tech Stack:** 1С:Предприятие 8.3.24, EDT 2026.1, русский BSL, YAxUnit 25.12, EDT-MCP.

## Global Constraints

- Изменять основной тестовый модуль `yaxunit/src/CommonModules/КОНС_Обр_Парсер_МО/Module.bsl`, отдельный opt-in модуль `КОНС_Обр_ПарсерБудущаяГрамматика_МО` и две документационные матрицы Task 7.
- Производственные модули `Парсер` и `ЭлементыМоделиЗапроса` в этой итерации не изменять.
- Вызывать только публичный метод `РазобратьВыражение(Текст)` реального объекта парсера из `КОНС_ТестовыеФабрикиСлужебный.СоздатьПарсер()`.
- Не вызывать и не мокировать приватные `НеТерминал*`, буфер токенов, таблицы первых символов и номера продукций.
- Проверять публичные поля AST: `Тип`, `Значение`, `Операция`, `ЛеваяЧасть`, `ПраваяЧасть`, `Выражение`, `Элементы`, `Имя` и специализированные поля узлов.
- Не добавлять тесты формы длинных цепочек операторов одного уровня: `1-2-3`, `8/4/2`, `A И B И C`. Их ожидаемая левая группировка документируется в отдельной acceptance-матрице.
- Проверять приоритет только между разными уровнями (`+` против `*`, `И` против `ИЛИ`) и группировку, явно заданную скобками.
- Каждый пакет: один корректный RED, одна guarded-запись всего пакета, один GREEN всего модуля; точечные повторы допустимы только для диагностики реального падения.
- Все тестовые обновления выполнять только с `updateScope="extension:yaxunit"`; `clean_project`, полный rebuild и `updateScope="all"` запрещены.
- Если зелёный характеристический тест обнаружит производственный дефект, не исправлять парсер в рамках этого плана: сохранить RED-доказательство, диагностировать и запросить отдельное решение.
- Тесты не читают и не записывают данные информационной базы и не используют транзакции.
