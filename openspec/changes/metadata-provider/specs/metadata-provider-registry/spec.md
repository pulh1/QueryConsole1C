## ADDED Requirements

### Requirement: Registry resolves table metadata providers by first name segment
Система SHALL иметь единый реестр поставщиков метаданных таблиц, который выбирает поставщика по первому сегменту полного имени таблицы до первой точки.

#### Scenario: Standard 1C table segment is routed to standard table provider
- **WHEN** реестр получает имя таблицы `Справочник.Номенклатура`
- **THEN** реестр MUST выбрать поставщика стандартных таблиц 1С для сегмента `Справочник`

#### Scenario: Executable view segment is routed to executable view provider
- **WHEN** реестр получает имя таблицы `ИсполняемоеПредставление.ДанныеСотрудников`
- **THEN** реестр MUST выбрать поставщика исполняемых представлений для сегмента `ИсполняемоеПредставление`

#### Scenario: Unknown segment is rejected
- **WHEN** реестр получает имя таблицы с незарегистрированным первым сегментом
- **THEN** реестр SHALL вернуть отсутствие поставщика или диагностируемую ошибку, не создавая источник неизвестного типа

### Requirement: Providers expose a shared metadata contract
Система SHALL использовать общий контракт поставщика для поиска таблицы, получения описания таблицы, полей, параметров и дочерних элементов иерархии UI.

#### Scenario: Query model requests table description
- **WHEN** обработка модели запроса добавляет источник по имени таблицы
- **THEN** она MUST получать описание источника через контракт поставщика, а не через отдельную ручную проверку каждого типа поставщика

#### Scenario: UI requests hierarchy children
- **WHEN** пользователь раскрывает группу или таблицу в дереве доступных таблиц конструктора
- **THEN** UI SHALL получать дочерние элементы через тот же контракт поставщика, который используется для разрешения таблицы в модели запроса

### Requirement: Standard table provider owns query schema lifetime
Поставщик стандартных таблиц 1С SHALL владеть экземпляром `СхемаЗапроса`, из которого получены `ДоступныеТаблицы`, и MUST не отдавать долгоживущие ссылки на элементы `ДоступныеТаблицы` за пределы безопасного жизненного цикла.

#### Scenario: Standard table fields are read while schema is alive
- **WHEN** UI или модель запроса запрашивает поля стандартной таблицы 1С
- **THEN** поставщик MUST читать данные через живую `СхемаЗапроса` или возвращать безопасную копию описания полей

#### Scenario: Registry is destroyed
- **WHEN** экземпляр реестра или поставщика стандартных таблиц уничтожен
- **THEN** ранее полученные долгоживущие данные UI SHALL оставаться безопасными только если они были скопированы в нейтральные структуры консоли

### Requirement: Executable view provider remains compatible with existing view descriptions
Поставщик исполняемых представлений SHALL использовать существующие описания и регистрацию исполняемых представлений, сохраняя поддержку таблиц вида `ИсполняемоеПредставление.*`.

#### Scenario: Existing executable view is resolved
- **WHEN** запрос содержит источник `ИсполняемоеПредставление.<ИмяПредставления>`
- **THEN** система MUST получить то же описание представления, поля, параметры, обработчик исполнения и генераторы, что и до рефакторинга

#### Scenario: Existing view manager methods stay valid
- **WHEN** существующая обработка представления предоставляет менеджерские методы `Описание()` и `ИмяПредставления()`
- **THEN** новый поставщик SHALL использовать их через адаптер без обязательного изменения каждой обработки представления

### Requirement: Query model processing uses registry for source resolution
Обработка модели запроса SHALL использовать реестр поставщиков при разрешении источников таблиц, сохраняя текущую семантику стандартных таблиц, временных таблиц, таблиц значений и исполняемых представлений.

#### Scenario: Existing standard table query is processed
- **WHEN** пользователь обрабатывает существующий запрос к стандартной таблице 1С
- **THEN** модель запроса MUST создать источник стандартной таблицы с совместимым именем, псевдонимом и полями

#### Scenario: Existing executable view query is processed
- **WHEN** пользователь обрабатывает существующий запрос к исполняемому представлению
- **THEN** модель запроса MUST создать источник исполняемого представления и применить параметры представления как до рефакторинга

#### Scenario: Unknown table is processed
- **WHEN** пользователь добавляет источник таблицы, отсутствующий во всех зарегистрированных поставщиках и доступных временных таблицах
- **THEN** система SHALL выдать ошибку уровня модели запроса о том, что таблица не найдена

### Requirement: Temporary tables are exposed through contextual provider
Система SHALL представлять временные таблицы пакета запроса через контекстный поставщик реестра, основанный на текущих `ОписанияВременныхТаблиц` и индексе запроса.

#### Scenario: Temporary table is available after placement
- **WHEN** предыдущий запрос пакета создал временную таблицу через `ПОМЕСТИТЬ`
- **THEN** поставщик временных таблиц MUST вернуть ее описание и поля для последующих запросов пакета

#### Scenario: Temporary table is destroyed
- **WHEN** запрос уничтожения удаляет временную таблицу из доступных описаний
- **THEN** поставщик временных таблиц SHALL перестать разрешать эту таблицу для последующих запросов пакета

#### Scenario: Constructor displays temporary table fields
- **WHEN** пользователь раскрывает доступную временную таблицу в дереве конструктора
- **THEN** UI MUST получить поля временной таблицы через контекстный поставщик реестра

### Requirement: Semantic model processing uses registry-backed context
Семантическая обработка модели запроса SHALL получать сведения о доступных таблицах и полях через реестр поставщиков или совместимый контекст, созданный в `ОбработкаМоделиЗапроса`.

#### Scenario: Expression processing resolves standard table fields
- **WHEN** `ОбработкаМоделиЗапроса.ОбработатьВыражение()` запускает `СемантическийАнализВыраженийПосетитель` для выражения со ссылкой на поле стандартной таблицы 1С
- **THEN** посетитель MUST получить сведения о таблице и поле из того же источника метаданных, который использовался при разрешении источника запроса

#### Scenario: Expression processing resolves executable view fields
- **WHEN** семантическая обработка проверяет выражение со ссылкой на поле исполняемого представления
- **THEN** система MUST использовать описание исполняемого представления из поставщика реестра и сохранить прежнюю проверку полей, параметров и типов

#### Scenario: Nested query context keeps registry access
- **WHEN** `ОбработкаМоделиЗапроса.КонтекстОбработкиВложенногоЗапроса()` создает контекст вложенного запроса
- **THEN** вложенный контекст SHALL сохранить доступ к реестру или совместимому источнику метаданных стандартных таблиц и исполняемых представлений

### Requirement: Query constructor UI uses registry for available table hierarchy
Конструктор запросов SHALL строить дерево доступных таблиц через реестр поставщиков, включая стандартные таблицы 1С и исполняемые представления, с ленивым раскрытием дочерних элементов.

#### Scenario: UI accesses registry through server methods
- **WHEN** клиентская форма конструктора запрашивает доступные таблицы или дочерние элементы дерева
- **THEN** она MUST обращаться к серверному методу формы или общего модуля, а не к объекту реестра напрямую

#### Scenario: Constructor opens available tables
- **WHEN** открывается форма конструктора запросов
- **THEN** UI MUST показать корневые группы доступных поставщиков без полного построения всех полей всех таблиц

#### Scenario: User expands executable view group
- **WHEN** пользователь раскрывает группу исполняемых представлений
- **THEN** UI SHALL получить дочерние группы и таблицы через поставщик исполняемых представлений и отобразить совместимые узлы дерева

#### Scenario: User expands table fields
- **WHEN** пользователь раскрывает стандартную таблицу или исполняемое представление
- **THEN** UI MUST отобразить поля из описания соответствующего поставщика в том же формате, который используется существующими командами добавления полей

### Requirement: Registry preserves performance characteristics
Система SHALL сохранять ленивое построение иерархии таблиц и MUST не выполнять полное сканирование всех полей всех поставщиков при открытии формы конструктора или при добавлении одного источника.

#### Scenario: Constructor opens with multiple providers
- **WHEN** в реестре зарегистрировано несколько поставщиков
- **THEN** открытие конструктора SHALL инициализировать только корневые данные и необходимые индексы поставщиков

#### Scenario: Single table is added programmatically
- **WHEN** код добавляет один источник через построитель модели запроса
- **THEN** система MUST обращаться только к поставщику, выбранному по первому сегменту имени таблицы, без перебора всех поставщиков

### Requirement: Existing public provider API remains available during migration
Система SHALL сохранить совместимость существующих публичных методов поставщика исполняемых представлений или предоставить фасады с тем же поведением на период миграции.

#### Scenario: Existing code calls executable view provider directly
- **WHEN** существующий код вызывает `ПоставщикИсполняемыхПредставлений.ОписаниеПредставленияПоИмениТаблицы()`
- **THEN** вызов MUST вернуть совместимое описание представления или `Неопределено` для неизвестной таблицы, как до рефакторинга

#### Scenario: Existing UI code requests executable view groups during migration
- **WHEN** оставшийся немигрированный код вызывает методы групп и дочерних групп исполняемых представлений
- **THEN** методы SHALL продолжить возвращать совместимые группы и имена таблиц
