## Context

Текущая архитектура использует несколько независимых источников знаний о таблицах. Стандартные таблицы 1С берутся из `СхемаЗапроса.ПакетЗапросов.Добавить(Тип("ЗапросВыбораСхемыЗапроса")).ДоступныеТаблицы`, а исполняемые представления разрешаются через `ПоставщикИсполняемыхПредставлений` и обработки `Представление*`.

Основные найденные точки использования:

- `ПостроительМоделиЗапроса.ДобавитьИсточник()` напрямую создает `СхемаЗапроса`, проверяет `ДоступныеТаблицы.Найти(ИмяИсточника)` и затем fallback-ом вызывает `ПоставщикИсполняемыхПредставлений.ОписаниеПредставленияПоИмениТаблицы()`.
- `ОбработкаМоделиЗапроса.КонтекстОбработкиВыражения()` создает `ВспомогательнаяСхема`, кладет `ДоступныеТаблицыИБ` в контекст и удерживает `__СхемаЗапрос`; этот контекст затем используется при обработке модели и выражений.
- `ОбработкаМоделиЗапроса.ОбработатьМодельЗапроса()` и `ОбработатьОператор()` ведут контекст пакета, временные таблицы, источники по псевдонимам и вызывают обработку исполняемых представлений до семантического обхода выражений.
- `ОбработкаМоделиЗапроса.ОбработатьВыражение()` создает `СемантическийАнализВыраженийПосетитель` с текущим контекстом, поэтому доступность таблиц и полей для семантики должна идти через тот же реестр или совместимый контекст.
- `ОбработкаПредставлениеЗапросов.ОбработатьИсточникЗапроса()` строково определяет исполняемое представление по префиксу `ИсполняемоеПредставление.` и заменяет обычный источник таблицы на модель исполняемого представления.
- `КонструкторЗапросовФормы.ЗаполнитьДочерниеЭлементыДереваДоступныхТаблиц()` раскрывает дерево UI через `ДоступныеТаблицыИБ`, временные таблицы и отдельную ветку исполняемых представлений.
- `ПоставщикИсполняемыхПредставлений` и `ПоставщикИсполняемыхПредставленийПовтИсп` уже содержат кэшируемые методы для описаний, групп и имен таблиц исполняемых представлений.

Ключевое ограничение платформы: объекты `ДоступныеТаблицы` и их дочерние элементы валидны только пока существует `СхемаЗапроса`, из которой они получены. Поэтому новый механизм не должен возвращать наружу долгоживущие ссылки на платформенные доступные таблицы без владельца жизненного цикла.

## Goals / Non-Goals

**Goals:**

- Ввести единый контракт поставщика метаданных таблиц для модели запроса и UI конструктора.
- Определять поставщика по первому сегменту полного имени таблицы.
- Сохранить поддержку стандартных таблиц 1С и исполняемых представлений без изменения синтаксиса запросов.
- Унифицировать временные таблицы как контекстный поставщик реестра, сохранив их доступность в рамках пакета запроса.
- Свести UI-иерархию таблиц и runtime-разрешение источников к одному механизму, чтобы новые поставщики подключались регистрацией, а не правками в нескольких модулях.
- Сохранить производительность за счет ленивого раскрытия и кэширования только безопасных данных.
- Сохранить существующие публичные методы через адаптеры на период миграции, если прямое удаление вызовов не требуется.

**Non-Goals:**

- Не создавать поставщик ClickHouse или другой новый внешний источник данных.
- Не менять язык запросов, лексер, парсер, AST и формат существующих запросов.
- Не переписывать исполнение исполняемых представлений и pushdown-оптимизации, кроме переноса точки получения описания.
- Не менять структуру описаний конкретных обработок `Представление*`, если их текущий контракт достаточен.
- Не выполнять массовое переименование существующих публичных методов и объектов без отдельной необходимости.

## Decisions

### Реестр поставщиков как объект обработки

Реестр метаданных таблиц реализуется как экземпляр обработки, который создается для сценария работы с моделью запроса или UI. Он хранит зарегистрированные поставщики, индекс по первому сегменту имени таблицы и состояние поставщиков, которым нужен жизненный цикл.

Альтернативы:

- Общий модуль-реестр проще вызывать, но в нем неудобно хранить `СхемаЗапроса` и другие временные объекты без глобального состояния или повторно используемого кэша.
- Менеджер обработки удобен как фабрика, но не подходит как основной владелец состояния конкретного экземпляра реестра.
- Объект обработки лучше всего соответствует задаче: может держать инициализированные поставщики, управлять временем жизни `СхемаЗапроса` и передаваться в модель запроса/UI как контекст.

Принятое решение: создать новый объект обработки `РеестрПоставщиковМетаданныхТаблиц` с фабричным публичным методом в менеджере или общем модуле-фасаде. Рабочее имя может быть уточнено при реализации по стилю существующих метаданных, но реестр не должен размещаться внутри существующей обработки конструктора или исполнителя.

### Единый контракт поставщика

Каждый поставщик должен предоставлять минимальный набор операций:

- `ПервыйСегмент()` или список сегментов, за которые отвечает поставщик.
- `ТаблицаСуществует(ИмяТаблицы)` для быстрой проверки источника.
- `ОписаниеТаблицы(ИмяТаблицы)` для модели запроса и семантического анализа.
- `ДочерниеЭлементы(ИдентификаторРодителя)` для ленивого дерева UI.
- `ПоляТаблицы(ИмяТаблицы)` для раскрытия полей в UI и проверки разыменований.
- `ПараметрыТаблицы(ИмяТаблицы)` для исполняемых представлений и будущих параметризованных источников.

Возвращаемые данные должны быть нейтральными структурами модели консоли, а не напрямую платформенными объектами `ДоступнаяТаблицаСхемыЗапроса`, если данные должны пережить конкретную операцию раскрытия.

### Формы реализации поставщиков

Поддерживаются три формы реализации, но через один адаптерный контракт реестра:

- Общий модуль: подходит для статeless-поставщика или поставщика, который использует только повторно используемые кэши и не владеет временными платформенными объектами.
- Объект обработки: подходит для поставщиков с состоянием, жизненным циклом, временными схемами, соединениями или локальными кэшами; это рекомендуемый вариант для стандартных таблиц 1С.
- Менеджер обработки: подходит для существующих обработок исполняемых представлений, где менеджер уже предоставляет `Описание()` и `ИмяПредставления()`; реестр должен использовать адаптер, а не требовать переписывания каждой обработки.

### Определение поставщика по первому сегменту

Реестр выделяет первый сегмент полного имени таблицы до первой точки и ищет зарегистрированного поставщика по этому сегменту.

Примеры:

- `Справочник.Номенклатура` → поставщик стандартных таблиц 1С для сегмента `Справочник`.
- `РегистрСведений.КадроваяИсторияСотрудников` → поставщик стандартных таблиц 1С для сегмента `РегистрСведений`.
- `ИсполняемоеПредставление.ДанныеСотрудников` → поставщик исполняемых представлений для сегмента `ИсполняемоеПредставление`.

Для стандартных таблиц поставщик регистрирует набор платформенных сегментов, которые доступны через `ДоступныеТаблицы`. Для неизвестного сегмента реестр возвращает `Неопределено` или ошибку уровня вызывающего сценария, сохраняя текущие тексты ошибок там, где это важно для совместимости.

Для временных таблиц используется контекстный поставщик с приоритетом после таблиц значений и до ошибки неизвестной таблицы. Так как имя временной таблицы обычно не имеет сегмента с точкой, реестр должен уметь передавать такие имена поставщику временных таблиц через контекст доступных временных таблиц, а не требовать глобальной регистрации каждого имени как сегмента.

### Жизненный цикл стандартных таблиц

Поставщик стандартных таблиц создает и удерживает собственный экземпляр `СхемаЗапроса` на время жизни поставщика. Все обращения к `ДоступныеТаблицы` выполняются через этот поставщик.

Реестр не должен кэшировать ссылки на элементы `ДоступныеТаблицы` дольше жизни поставщика. Для UI допускается кэшировать нормализованные узлы дерева и описания полей, если они скопированы в структуры/массивы и не содержат ссылок на уничтоженную схему.

### Адаптер существующих исполняемых представлений

Поставщик исполняемых представлений в новом реестре должен использовать текущий `ПоставщикИсполняемыхПредставлений` как источник описаний и иерархии. Это сохраняет существующие обработки `Представление*`, методы `Описание()`, `ИмяПредставления()` и повторно используемый кэш `ПоставщикИсполняемыхПредставленийПовтИсп`.

Существующие публичные методы `ПоставщикИсполняемыхПредставлений` остаются совместимыми. После внедрения они могут стать фасадом к новому поставщику или продолжить обслуживать только внутреннюю регистрацию исполняемых представлений.

### Использование в модели запроса и UI

`ПостроительМоделиЗапроса.ДобавитьИсточник()` должен получать реестр из контекста построителя или создавать его через фабрику. Вместо самостоятельного создания `СхемаЗапроса` и fallback-а в `ПоставщикИсполняемыхПредставлений` метод должен запросить у реестра описание источника.

`ОбработкаПредставлениеЗапросов.ОбработатьИсточникЗапроса()` должна либо использовать признак типа источника, установленный при разрешении через реестр, либо обращаться к реестру для получения описания исполняемого представления. Строковый префикс `ИсполняемоеПредставление.` можно оставить как совместимый быстрый фильтр, но он не должен быть единственным местом знания о поставщике.

`КонструкторЗапросовФормы` должен строить дерево доступных таблиц через серверные методы формы или серверный общий модуль, который владеет экземпляром реестра. Клиентский код UI не должен обращаться к реестру напрямую. Корневые узлы поставщиков, ленивое раскрытие групп, таблиц и полей, а также временные таблицы должны проходить через единые нейтральные структуры узлов.

### Временные таблицы как поставщик

Временные таблицы включаются в реестр как контекстный поставщик, зависящий от `ОписанияВременныхТаблиц` текущего пакета запроса и индекса запроса. Он должен покрывать текущие сценарии `ИсточникДанныхВременнаяТаблица`, раскрытие полей временной таблицы в UI и семантическую проверку ссылок на поля ВТ.

Поставщик временных таблиц не является глобальным: он создается или обновляется вместе с контекстом обработки модели запроса и UI формы. При выполнении `ПОМЕСТИТЬ` и уничтожении ВТ поставщик должен видеть актуальное состояние `ОписанияВременныхТаблиц` так же, как текущий код в `ОбработкаМоделиЗапроса.ОбработатьМодельЗапроса()`.

### Семантическая обработка модели запроса

`ОбработкаМоделиЗапроса` является отдельной точкой интеграции, а не только потребителем результата построителя. Контекст, создаваемый в `КонтекстОбработкиВыражения()`, должен получить реестр или совместимый объект доступа к метаданным таблиц вместе с существующими полями `ДоступныеТаблицыИБ`, `ИспользуемыеТаблицы`, `ИсточникиПоИдентификаторам` и `ОписанияВременныхТаблиц`.

При обработке оператора реестр должен быть доступен до вызова `ОбработкаПредставлениеЗапросов.ОбработатьИсточникЗапроса()`, обработки параметров виртуальных таблиц, группировок, условий, соединений и выбираемых полей. Это гарантирует, что `СемантическийАнализВыраженийПосетитель` получает те же сведения о таблицах и полях, что UI и построитель модели.

Для обратной совместимости на первом этапе допустимо оставить `ДоступныеТаблицыИБ` в контексте как адаптер к поставщику стандартных таблиц, но новым источником истины для разрешения таблиц должен стать реестр.

## Свойства корректности

- Одна и та же таблица должна разрешаться одинаково при добавлении источника в модель запроса и при выборе в UI.
- Одна и та же таблица должна разрешаться одинаково при построении модели, семантической обработке `ОбработкаМоделиЗапроса` и выборе в UI.
- Временная таблица должна разрешаться через тот же реестр, но с учетом контекста пакета запроса и текущего индекса запроса.
- Стандартные таблицы 1С не должны использовать объекты `ДоступныеТаблицы` после уничтожения владельца `СхемаЗапроса`.
- Исполняемые представления должны получать те же описания, поля, параметры, обработчики исполнения и генерации кода, что и до рефакторинга.
- Неизвестная таблица должна приводить к тем же или более точным ошибкам, без молчаливого создания некорректного источника.
- Ленивое раскрытие дерева UI не должно строить полную иерархию всех поставщиков при открытии формы.

## Совместимость

- Существующие запросы к стандартным таблицам 1С и `ИсполняемоеПредставление.*` должны выполняться без изменения текста.
- Публичные вызовы `ПоставщикИсполняемыхПредставлений.ОписаниеПредставленияПоИмениТаблицы()`, `ГруппыИсполняемыхПредставлений()`, `ИменаДочернихГрупп()` и родственных методов должны остаться доступными или быть заменены совместимыми фасадами.
- ЗУП-специфичные обработки представлений и их менеджеры не должны знать о новом реестре.
- Генерация BSL-кода, генерация запросов для СКД и универсальный отчет должны получать совместимые описания источников.

## Risks / Trade-offs

- [Risk] Реестр начнет удерживать устаревшие платформенные объекты `ДоступныеТаблицы` после уничтожения схемы запроса → [Mitigation] Владельцем `СхемаЗапроса` является поставщик стандартных таблиц, а наружу выдаются копии данных или краткоживущие значения в рамках метода.
- [Risk] UI потеряет производительность из-за полной перестройки иерархии поставщиков → [Mitigation] Корневые узлы строятся быстро, дочерние элементы загружаются лениво, кэшируются только нормализованные узлы и индексы.
- [Risk] Совместимость исполняемых представлений нарушится из-за нового контракта → [Mitigation] Первый этап использует адаптер к существующему `ПоставщикИсполняемыхПредставлений`, без изменения обработок `Представление*`.
- [Risk] Появится дублирование между старым поставщиком исполняемых представлений и новым реестром → [Mitigation] Новый реестр становится точкой orchestration, старый поставщик остается специализированным адаптером/фасадом до завершения миграции вызовов.
- [Risk] Разные сценарии создадут разные экземпляры реестра и получат разные кэши → [Mitigation] Фабрика реестра должна явно разделять режимы: краткоживущий реестр для обработки запроса и серверный экземпляр для UI формы.
- [Risk] Унификация временных таблиц смешает глобальные поставщики и контекст пакета запроса → [Mitigation] Поставщик временных таблиц должен быть контекстным, не кэшироваться глобально и обновляться из `ОписанияВременныхТаблиц` текущего пакета.

## Migration Plan

1. Добавить контракт и фабрику реестра без изменения существующих вызовов.
2. Реализовать поставщик стандартных таблиц 1С с собственным владельцем `СхемаЗапроса`.
3. Реализовать поставщик исполняемых представлений как адаптер к текущему `ПоставщикИсполняемыхПредставлений`.
4. Реализовать контекстный поставщик временных таблиц на основе `ОписанияВременныхТаблиц` и индекса запроса пакета.
5. Перевести `ПостроительМоделиЗапроса.ДобавитьИсточник()` на разрешение источника через реестр, сохранив тексты ошибок и параметры исполняемых представлений.
6. Перевести UI конструктора на получение корневых и дочерних узлов через серверные методы, работающие с реестром.
7. Перевести семантический анализ и обработку исполняемых представлений на получение описаний через реестр там, где это устраняет прямые знания о поставщиках.
8. Оставить совместимые фасады старых методов и удалить дублирующую логику только после прохождения проверок.

Rollback: поскольку синтаксис и формат запросов не меняются, откат должен сводиться к возврату старых точек получения `ДоступныеТаблицы` и `ПоставщикИсполняемыхПредставлений` в измененных модулях.

## Open Questions

Нет открытых вопросов по ключевым архитектурным решениям: реестр создается как новый объект обработки, UI работает с ним только через серверные методы, временные таблицы входят в единый механизм как контекстный поставщик.
