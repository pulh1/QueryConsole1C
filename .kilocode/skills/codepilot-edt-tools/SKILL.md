# Инструменты CodePilot EDT

Используй CodePilot1C как основной путь для EDT-aware работы с 1C.

## Иерархия инструментов

Инструменты CodePilot раскрываются лениво.

1. Загружай workflow-подсказки, когда это полезно для задачи.
2. Перед использованием предметных инструментов сначала обнаружь нужную категорию инструментов.
3. После discovery вызывай раскрытые инструменты напрямую.
4. Если нужный инструмент недоступен, сначала попробуй discovery для соответствующей категории и только потом переходи к fallback.

## Определение имени проекта

Перед вызовом инструментов CodePilot, которым требуется имя проекта, определи имя EDT-проекта.

Используй следующий порядок:

1. Если пользователь указал имя EDT-проекта, используй его.
2. Если текущий workspace или репозиторий содержит Eclipse/EDT-файлы `.project`, прочитай их и используй значение XML `<projectDescription><name>...</name>`.
3. Если найден ровно один файл `.project`, используй его `<name>` как имя проекта по умолчанию.
4. Если найдено несколько файлов `.project`, предпочитай тот, который находится под активным корнем репозитория/конфигурации. Если неоднозначность остаётся, спроси пользователя, какой EDT-проект использовать.
5. Перед изменениями подтверди имя read-only вызовом CodePilot.

Пример для PowerShell:

```powershell
Get-ChildItem -Force -Recurse -Filter .project -Path . |
  ForEach-Object {
    $xml = [xml](Get-Content -LiteralPath $_.FullName -Raw)
    [pscustomobject]@{ Path = $_.FullName; ProjectName = $xml.projectDescription.name }
  }
```

Не определяй имя EDT-проекта только по имени папки репозитория, если доступен `.project`.

## Порядок изменения метаданных

Никогда не редактируй `.mdo` или сгенерированные EDT metadata-файлы вручную, если изменение можно выполнить через EDT-aware инструмент CodePilot.

Для изменений метаданных, форм, СКД, расширений и внешних объектов используй порядок:

1. Сначала изучи текущее состояние объекта.
2. Провалидируй точный payload изменения, если инструмент поддерживает или требует валидацию.
3. Выполни изменение, используя провалидированный payload или возвращённый `validation_token`.
4. Проверь результат после изменения через диагностику.

`validation_token` привязан к точному payload. Если payload меняется, выполни валидацию заново.

## Формы

Перед редактированием существующей формы сначала изучи её текущую структуру.

Для форм предпочитай инструменты, которые умеют безопасно работать с моделью формы и layout. Не привязывай визуальное поле к предполагаемому `data_path`; сначала проверь или создай соответствующий реквизит формы.

## BSL

Используй семантические BSL-инструменты CodePilot перед широкими текстовыми изменениями.

Особенно это важно, когда нужно получить:

* список методов;
* сигнатуры;
* тела методов;
* ссылки на методы;
* контекст модуля;
* область видимости;
* информацию о символах или типах.

Для простого текстового поиска, быстрой навигации и небольших локальных правок `.bsl` допустим файловый поиск и чтение файлов.

Если модуль ещё не материализован как `.bsl` файл, сначала материализуй его через EDT-aware инструмент.

## QA и диагностика

Используй релевантные инструменты QA и диагностики, когда задача требует проверки через YAxUnit, Vanessa QA, диагностику метаданных, обновление ИБ или похожий workflow.

Не утверждай, что диагностика, тесты или обновление ИБ были выполнены, если они фактически не запускались.

## Ограничения

* Предпочитай EDT-aware инструменты CodePilot ручному редактированию файлов для метаданных, форм, СКД, расширений и внешних объектов.
* Не вызывай изменяющие инструменты без валидации, если инструмент требует `validation_token`.
* Перед изменением перечитывай фактическое состояние проекта; не полагайся только на описание задачи из OpenSpec.
* Проверяй диагностику после каждого изменения, если доступен подходящий инструмент.
* Если инструмент CodePilot недоступен, сначала вызови discovery для соответствующей категории и только потом переходи к fallback.
