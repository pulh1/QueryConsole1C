
# Стиль BSL-кода

Проект разрабатывается на BSL для 1С:Предприятие. При изменении кода соблюдай стиль существующего проекта.

## Общие принципы

* Предпочитай стандартные механизмы платформы 1С.
* Предпочитай методы БСП, если они уже используются в проекте и подходят для задачи.
* Не придумывай собственную инфраструктуру, если задача решается штатным механизмом.
* Не меняй публичный программный интерфейс без необходимости.
* Не добавляй новые зависимости без явной причины.
* Не делай большие переписывания кода, если задача требует точечного исправления.
* Не смешивай смысловые изменения с массовым автоформатированием.
* Не используй псевдокод в изменениях проекта: код должен быть готов к выполнению.

## Именование

Имена должны быть осмысленными и соответствовать терминам предметной области.

Процедуры называй от действия:

```bsl
Процедура ЗагрузитьКонтрагента()
Процедура РассчитатьСуммуДокумента()
```

Функции называй по возвращаемому значению:

```bsl
Функция ПолноеИмяПользователя()
Функция ДокументПроведен()
Функция НовыеПараметрыЗаполнения()
```

Флаги называй по истинному состоянию:

```bsl
ЕстьОшибки = Ложь;
ЭтоНовыйДокумент = Истина;
```

Избегай отрицательных флагов:

```bsl
// Нежелательно
НетОшибок = Истина;
НеНужноЗаполнять = Ложь;
```

Не используй слишком общие имена переменных, если по коду не очевиден смысл:

```bsl
// Нежелательно
Объект = ...
Данные = ...
Результат = ...
```

Исключение — короткие локальные участки, где смысл очевиден.

## Структура модулей

Сохраняй существующую структуру областей модуля.

Если создаёшь новый модуль или добавляешь крупный блок, используй стандартные области:


Не добавляй область, если она не нужна.

## Описания методов

Если в модуле уже используются описания методов, добавляй описание в том же стиле.

Описание должно объяснять назначение метода, параметры и возвращаемое значение.

Пример:

```bsl
// Заполняет параметры обработки строки документа.
//
// Параметры:
//  СтрокаДокумента - СтрокаТабличнойЧасти - строка табличной части документа.
//  ПараметрыЗаполнения - Структура - параметры заполнения.
//
// Возвращаемое значение:
//  Структура - заполненные параметры обработки.
//
Функция ПараметрыОбработкиСтроки(СтрокаДокумента, ПараметрыЗаполнения)
```

Не пиши описание, которое просто повторяет имя метода.

## Форматирование

* Сохраняй форматирование существующего файла.
* Не делай искусственные переносы без необходимости.
* Не меняй форматирование всего файла ради небольшой правки.
* Для новых участков кода используй читаемое форматирование с пустыми строками между смысловыми блоками.

Пример:

```bsl
Процедура ЗаполнитьДанныеПоКонтрагенту(Контрагент)

    Если Контрагент = Неопределено Тогда
        Возврат;
    КонецЕсли;

    ТекущаяДата = ОбщегоНазначения.ПолучитьРабочуюДату();
    ТекущийГод = Год(ТекущаяДата);

КонецПроцедуры
```

## Запросы

* Используй параметры запроса `&Параметр`.
* Не конкатенируй пользовательские значения в текст запроса.
* Для сложных запросов используй временные таблицы.
* Форматируй запрос многострочно.
* Не меняй алиасы и структуру запроса без необходимости.

Пример:

```bsl
ТекстЗапроса =
"ВЫБРАТЬ
|    Контрагенты.Ссылка КАК Ссылка,
|    Контрагенты.Наименование КАК Наименование
|ИЗ
|    Справочник.Контрагенты КАК Контрагенты
|ГДЕ
|    Контрагенты.ИНН = &ИНН";

Запрос = Новый Запрос(ТекстЗапроса);
Запрос.УстановитьПараметр("ИНН", ИНН);
```

## Ошибки и логирование

* Не используй `Попытка ... Исключение` для обычного контроля потока.
* Не подавляй исключения без объяснимой причины.
* Не используй `Сообщить()` для логирования, если пользователь явно этого не просил.
* Не используй `ЗаписьЖурналаРегистрации()` без явного требования задачи.
* Если ошибка требует обработки, делай обработку явно и предметно.

## Проверка после изменений

После изменения BSL-кода по возможности выполни доступную диагностику проекта или модуля.

В финальном ответе явно укажи:

* какие файлы изменены;
* какая диагностика запускалась;
* какие ошибки остались;
* что не удалось проверить.
