# План исправления реализации metadata-provider

## Цель

Довести текущую реализацию реестра поставщиков метаданных таблиц до задумки из `openspec/changes/metadata-provider/proposal.md` и `design.md`: единый расширяемый механизм поставщиков, корректный жизненный цикл `СхемаЗапроса`, единый контракт для модели запроса, семантики и UI, а также соответствие ООП-паттернам проекта.

## Принципы исправления

- Не менять синтаксис запросов, AST, лексер и парсер.
- Сохранить совместимость существующих запросов и `ИсполняемоеПредставление.*`.
- Не переписывать обработки `Представление*` и их менеджеры.
- Не редактировать `.mdo` вручную, если изменение можно выполнить через EDT-aware инструменты.
- Не делать массовый рефакторинг вне зоны `metadata-provider`.
- Исправлять через малые шаги с проверкой после каждого смыслового блока.

## Зафиксированные решения

- Поставщики реализуются отдельными обработками-поставщиками с методами контракта. Вариант со структурами-адаптерами не используем.
- Алгоритм `РазрешитьПоставщика()` по первому сегменту не меняем: если имя таблицы содержит точку, реестр выбирает поставщика по первому сегменту. Если имя без точки, это временная таблица или таблица значений, и она обрабатывается отдельным контекстным путём.
- Контекстный поставщик временных таблиц не должен перехватывать имена с точкой и не должен использоваться как fallback для неизвестной таблицы зарегистрированного сегмента.

## 1. Стабилизировать контракт реестра и DTO

### 1.1. Ввести явные нейтральные DTO

Файл: `QueryConsoleZUP/src/DataProcessors/РеестрПоставщиковМетаданныхТаблиц/ObjectModule.bsl`

Нужно закрепить единый формат возвращаемых данных:

- `ОписаниеТаблицыПоставщикаМетаданных`;
- `ПолеТаблицыПоставщикаМетаданных`;
- `ПараметрТаблицыПоставщикаМетаданных`;
- `ЭлементИерархииПоставщикаМетаданных`.

Для UI в DTO должны быть все данные, чтобы форма не знала конкретный вид поставщика:

- `ТипУзла` или аналог: `ГруппаПоставщика`, `ГруппаТаблиц`, `Таблица`, `Поле`;
- `Идентификатор`;
- `Представление`;
- `ЕстьДочерниеЭлементы`;
- `ТипЗначения`;
- `Картинка` или нейтральный признак картинки;
- `ИмяПоставщика` только как технический маршрут для следующего раскрытия.

Критерий готовности: `КонструкторЗапросовФормы` не должен ветвиться по строкам `"ИсполняемыеПредставления"` / `"ВременныеТаблицы"` для базового отображения дерева.

### 1.2. Убрать небезопасное копирование платформенных полей

Файл: `QueryConsoleZUP/src/DataProcessors/РеестрПоставщиковМетаданныхТаблиц/ObjectModule.bsl`

Исправить `КопияПолейДоступнойТаблицы()` так, чтобы она различала:

- `ДоступноеПолеСхемыЗапроса`;
- `ДоступнаяВложеннаяТаблицаСхемыЗапроса`.

Для вложенной таблицы нельзя обращаться к `ТипЗначения` и `Роль`; нужно копировать `Имя` и `Поля`, а тип узла указывать нейтрально как вложенную таблицу.

Критерий готовности: описание стандартной таблицы с вложенными таблицами не падает при раскрытии полей.

## 2. Перевести поставщиков ближе к ООП-паттерну

### 2.1. Убрать централизованный type-code dispatch

Файл: `QueryConsoleZUP/src/DataProcessors/РеестрПоставщиковМетаданныхТаблиц/ObjectModule.bsl`

Сейчас поведение поставщиков реализовано через:

- `ПоставщикТаблицаСуществует()`;
- `ПоставщикОписаниеТаблицы()`;
- `ПоставщикДочерниеЭлементы()`;
- проверки `Поставщик.Тип = ...`.

Нужно заменить это на объектный контракт через отдельные обработки-поставщики. Реестр должен хранить экземпляры объектов поставщиков и делегировать им операции, а не определять поведение по строковому `Тип`.

Планируемые обработки:

- `ПоставщикМетаданныхСтандартныхТаблиц`;
- `ПоставщикМетаданныхИсполняемыхПредставлений`;
- `ПоставщикМетаданныхВременныхТаблиц`.

Новые объекты метаданных создавать только EDT-aware способом. Обработки `Представление*` не менять: поставщик исполняемых представлений остаётся адаптером к существующему `ПоставщикИсполняемыхПредставлений`.

Минимальный контракт поставщика:

```bsl
Сегменты()
ИмяПоставщика()
КорневыеЭлементы()
ТаблицаСуществует(ИмяТаблицы)
ОписаниеТаблицы(ИмяТаблицы)
ПоляТаблицы(ИмяТаблицы)
ПараметрыТаблицы(ИмяТаблицы)
ДочерниеЭлементы(ИдентификаторРодителя)
```

Критерий готовности: новый поставщик добавляется созданием обработки-поставщика и регистрацией её экземпляра в реестре, без изменения центральных диспетчеров `ПоставщикТаблицаСуществует`, `ПоставщикОписаниеТаблицы`, `ПоставщикДочерниеЭлементы`.

### 2.2. Зафиксировать стратегию выбора поставщика без fallback по сегментным именам

Файл: `QueryConsoleZUP/src/DataProcessors/РеестрПоставщиковМетаданныхТаблиц/ObjectModule.bsl`

Алгоритм `РазрешитьПоставщика()` не меняем в части сегментных имён:

1. Если имя содержит точку, выделить первый сегмент.
2. Найти поставщика по первому сегменту.
3. Если поставщик найден, вернуть его.
4. Если поставщик не найден, вернуть `Неопределено`.
5. Если имя не содержит точку, считать его кандидатом во временную таблицу или таблицу значений и обрабатывать через существующий контекстный путь.

Следствие: временные таблицы считаются одноcегментными именами. Они не должны конкурировать с сегментными поставщиками и не должны использоваться как fallback для имён вида `Справочник.НеизвестнаяТаблица`.

Критерий готовности: `Справочник.*` маршрутизируется только в поставщик стандартных таблиц, `ИсполняемоеПредставление.*` только в поставщик исполняемых представлений, а имя без точки проверяется как временная таблица/таблица значений.

## 3. Исправить UI-иерархию конструктора

### 3.1. Строить корень дерева через реестр

Файл: `QueryConsoleZUP/src/DataProcessors/КонструкторЗапросов/Forms/КонструкторЗапросов/Module.bsl`

Метод `ЗаполнитьСписокДоступныхТаблиц()` должен получать корневые элементы через серверный реестр:

- стандартные таблицы;
- исполняемые представления;
- временные таблицы, если они доступны;
- будущие поставщики без правки формы.

Старое прямое добавление `ДоступныеТаблицыИБ` можно временно оставить только как совместимый fallback, но основной путь должен идти через `РеестрПоставщиковМетаданныхТаблицФормы().ДочерниеЭлементы()`.

Критерий готовности: новый зарегистрированный поставщик появляется в корне дерева без отдельной правки формы.

### 3.2. Исправить раскрытие стандартных сегментов

Файл: `QueryConsoleZUP/src/DataProcessors/РеестрПоставщиковМетаданныхТаблиц/ObjectModule.bsl`

Сейчас `ЭлементыИерархииСтандартныхТаблиц("Справочник")` возвращает пустой список, потому что сегмент трактуется как имя таблицы.

Нужно реализовать ленивую иерархию стандартных таблиц:

- `Неопределено` -> корневой поставщик/группы сегментов;
- `Справочник` -> дочерние таблицы сегмента;
- `Справочник.Номенклатура` -> поля таблицы;
- вложенная таблица -> её поля.

При построении таблиц сегмента нельзя раскрывать поля всех таблиц.

Критерий готовности: раскрытие `Справочник` показывает таблицы, а раскрытие конкретной таблицы показывает поля.

### 3.3. Убрать знание видов поставщиков из UI

Файл: `QueryConsoleZUP/src/CommonModules/КонструкторЗапросовФормы/Module.bsl`

Метод `ДобавитьЭлементВДеревоТаблиц()` должен работать с нейтральными DTO. Ветвления по конкретным поставщикам допустимы только временно как fallback для старых структур.

Критерий готовности: UI не содержит обязательных веток для каждого нового поставщика.

## 4. Исправить lifecycle временных таблиц в форме

### 4.1. Инвалидировать или пересоздавать реестр при изменении ВТ

Файл: `QueryConsoleZUP/src/DataProcessors/КонструкторЗапросов/Forms/КонструкторЗапросов/Module.bsl`

Сейчас `мРеестрПоставщиковМетаданныхТаблиц` создаётся один раз, а список ВТ изменяется позднее. Нужно:

- либо пересоздавать реестр в `РеестрПоставщиковМетаданныхТаблицФормы()` каждый раз из актуального временного хранилища;
- либо сбрасывать `мРеестрПоставщиковМетаданныхТаблиц = Неопределено` в `ОписаниеДоступныхВТВоВременноеХранилище()`.

Предпочтительно второе: сохранить кэш, но явно инвалидировать его при изменении состояния.

Критерий готовности: после смены запроса, создания или уничтожения ВТ реестр формы видит актуальные временные таблицы.

### 4.2. Учитывать индекс текущего запроса пакета в UI-реестре

Файлы:

- `QueryConsoleZUP/src/DataProcessors/РеестрПоставщиковМетаданныхТаблиц/ManagerModule.bsl`;
- `QueryConsoleZUP/src/DataProcessors/КонструкторЗапросов/Forms/КонструкторЗапросов/Module.bsl`.

`СоздатьДляФормы()` сейчас передаёт индекс `-1`. Для корректной доступности ВТ в пакете нужно передавать текущий `ИндексЗапроса` формы.

Критерий готовности: ВТ доступна только в тех запросах пакета, где она действительно должна быть доступна.

## 5. Уточнить жизненный цикл `СхемаЗапроса`

### 5.1. Сделать реестр владельцем стандартной схемы

Файл: `QueryConsoleZUP/src/CommonModules/ОбработкаМоделиЗапроса/Module.bsl`

Сейчас контекст создаёт `__СхемаЗапрос` и `ДоступныеТаблицыИБ`, а реестр создаёт свою схему. Нужно выбрать один источник истины.

С учётом `design.md` предпочтительно:

- стандартный поставщик внутри реестра владеет `СхемаЗапроса`;
- `ДоступныеТаблицыИБ` в контексте оставить только как compatibility fallback на время миграции;
- новые проверки и семантика должны использовать реестр.

Критерий готовности: новые сценарии не зависят от `Контекст.ДоступныеТаблицыИБ` для разрешения источника и полей.

### 5.2. Не пересоздавать стандартный реестр без необходимости

Файл: `QueryConsoleZUP/src/CommonModules/ОбработкаМоделиЗапроса/Module.bsl`

Сейчас реестр пересоздаётся при каждом изменении индекса запроса пакета. Нужно рассмотреть обновление только контекстного поставщика временных таблиц, чтобы стандартный поставщик и его схема не создавались многократно.

Минимальный безопасный вариант: оставить пересоздание для корректности, но зафиксировать TODO/следующий шаг только если производительность станет проблемой.

Критерий готовности: нет рассинхронизации между реестром и актуальным состоянием ВТ.

## 6. Довести интеграцию модели и семантики

### 6.1. Проверить обработку исполняемых представлений

Файлы:

- `QueryConsoleZUP/src/CommonModules/ОбработкаПредставлениеЗапросов/Module.bsl`;
- `QueryConsoleZUP/src/CommonModules/СемантическийАнализВыраженийУтилиты/Module.bsl`.

Нужно сохранить fallback на `ПоставщикИсполняемыхПредставлений`, но основной путь должен идти через реестр, если он есть и инициализирован.

Также нужно защитить проверки вида:

```bsl
Если Контекст.Свойство("РеестрПоставщиковМетаданныхТаблиц") Тогда
```

от значения `Неопределено`.

Критерий готовности: внешний контекст без инициализированного реестра не приводит к ошибке вызова метода у `Неопределено`.

### 6.2. Проверить `ПостроительМоделиЗапроса.ДобавитьИсточник()`

Файл: `QueryConsoleZUP/src/DataProcessors/ПостроительМоделиЗапроса/ObjectModule.bsl`

Нужно убедиться, что:

- стандартная таблица создаётся как `ИсточникДанныхТаблица`;
- исполняемое представление создаётся как `ИсполняемоеПредставление`;
- неизвестная таблица даёт прежнюю или более точную ошибку;
- параметры представления не устанавливаются, если источник не является исполняемым представлением.

Критерий готовности: поведение старых публичных сценариев не меняется.

## Рекомендуемый порядок реализации

1. Исправить безопасное копирование полей стандартных таблиц.
2. Исправить lifecycle реестра формы и индекс текущего запроса пакета.
3. Довести стандартный provider hierarchy: сегмент -> таблицы -> поля.
4. Перевести корень UI-дерева на `ДочерниеЭлементы()` реестра.
5. Убрать provider-specific ветвления из UI, насколько возможно без большого переписывания.
6. Создать отдельные обработки-поставщики и заменить центральные `Если Поставщик.Тип = ...` на делегирование их методам.
7. Укрепить проверки `РеестрПоставщиковМетаданныхТаблиц <> Неопределено` в семантике.
8. Добавить недостающие тесты.
9. Запустить диагностику и регрессионные сценарии.

## Handoff Для Новой Сессии

Реализацию выполнять в новой сессии по этому плану. Перед началом новой сессии исполнитель должен перечитать:

- `openspec/changes/metadata-provider/proposal.md`;
- `openspec/changes/metadata-provider/design.md`;
- `openspec/changes/metadata-provider/specs/metadata-provider-registry/spec.md`;
- этот план: `.kilo/plans/1781589700845-silent-rocket.md`.

Ключевые решения, которые нельзя менять без нового согласования:

- поставщики делаются отдельными обработками-поставщиками;
- структуры-адаптеры не использовать как основной вариант;
- `РазрешитьПоставщика()` не должен fallback-иться в поставщик временных таблиц для имён с точкой;
- имя без точки считается временной таблицей или таблицей значений;
- метаданные новых обработок создавать только EDT-aware инструментами CodePilot1C.

Начинать реализацию нужно с read-only проверки актуального состояния ветки и текущих изменённых файлов, потому что в рабочем дереве уже есть незакоммиченные изменения.

## Риски

- Полный перевод стандартного дерева на реестр может затронуть существующее поведение отображения групп платформы. Нужно сравнить визуальную структуру до/после.
- Удалять старые fallback-вызовы рано рискованно; лучше оставить их на период миграции, но сделать новый путь основным.
- Создание отдельных обработок-поставщиков потребует изменения метаданных через EDT-aware инструменты; ручные правки `.mdo` не допускаются.
