# AGENTS.md

## Общие правила

* Всегда отвечай пользователю на русском языке, если он явно не попросил другой язык.
* Отвечай кратко и по делу: сначала практический вывод, затем детали.
* Если задача связана с кодом, давай готовый для вставки код, а не псевдокод.
* Не выдумывай метаданные, имена модулей, методы, свойства объектов и API платформы.
* Если информации недостаточно, явно укажи допущения или задай уточняющий вопрос.
* Предпочитай стандартные механизмы платформы 1С и БСП вместо самописных решений.
* Перед значимыми изменениями сначала изучи текущую структуру проекта и существующий код.

## Контекст проекта

Проект разрабатывается для 1С:Предприятие.

Основной стек:

* 1С:Предприятие 8.3.27;
* 1C:EDT;
* BSL;
* проектная структура EDT;
* работа с метаданными, управляемыми формами, модулями, СКД и расширениями.

Если доступны инструменты CodePilot1C / EDT MCP, используй их для анализа проекта, поиска метаданных, проверки модулей, диагностики и безопасной работы с EDT-структурой.

## Терминал и PowerShell

Среда по умолчанию — Windows PowerShell.

Перед выполнением команд учитывай синтаксис PowerShell. Не генерируй bash-style escaping, если явно не запущен bash.


## Безопасность изменений

Не выполняй destructive/broad changes без явного подтверждения пользователя.

К таким операциям относятся:

* удаление файлов;
* удаление объектов метаданных;
* массовый рефакторинг;
* массовое изменение форм;
* изменение большого количества модулей;
* обновление информационной базы;
* ручное изменение сгенерированных EDT metadata-файлов, если доступен EDT-aware/MCP-инструмент для этой операции;
* изменение `.mdo`, если есть EDT-aware инструмент для такой операции.

Для метаданных, форм, СКД, расширений и внешних объектов предпочитай EDT-aware инструменты CodePilot1C / EDT MCP, если они доступны.

Обычные `.bsl` файлы можно редактировать файловыми инструментами, но перед нетривиальными изменениями сначала изучи контекст модуля, существующие методы и ссылки.

## Правила работы с 1С / BSL

* Соблюдай стиль существующего кода проекта.
* Не меняй публичный программный интерфейс без необходимости.
* Не добавляй новые зависимости, если задача решается штатными средствами.
* Не используй `Попытка ... Исключение` для обычного контроля потока.
* Не используй `Сообщить()` для логирования, если пользователь явно этого не просил.
* Не используй `ЗаписьЖурналаРегистрации()` без явного требования задачи.
* Для запросов используй параметры `&Параметр`, а не конкатенацию пользовательских значений в текст запроса.
* Для сложных запросов предпочитай читаемое форматирование и временные таблицы.
* При добавлении новых методов пиши описание в стиле проекта, если в модуле уже используются описания методов.

## Работа с CodePilot1C / EDT MCP

Если задача связана с EDT, метаданными, формами, СКД, расширениями, диагностикой или анализом BSL-кода:

* используй доступные CodePilot1C / EDT MCP инструменты;
* сначала выполняй read-only анализ;
* перед изменениями перечитывай актуальное состояние объекта;
* не полагайся только на текст задачи или старое описание;
* после изменений проверяй диагностику проекта, если доступен соответствующий инструмент.

Если доступен skill `codepilot-edt-tools`, используй его для подробного workflow по CodePilot1C.

## Антигаллюцинации

Никогда не предполагай, что объект, реквизит, метод, модуль или API существует.

Перед использованием проверь:

* наличие объекта метаданных;
* наличие модуля;
* наличие метода;
* сигнатуру метода;
* область выполнения кода;
* доступность платформенного или БСП API.

Если проверить невозможно, явно напиши, что это предположение.

## Финальный ответ пользователю

В финальном ответе указывай:

* что было сделано;
* какие файлы изменены;
* какие проверки выполнены;
* какие ошибки остались, если они есть;
* что требует ручной проверки пользователя.

Не утверждай, что проверка выполнена, если она фактически не запускалась.
